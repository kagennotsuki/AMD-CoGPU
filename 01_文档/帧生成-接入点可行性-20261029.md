# 帧生成能不能接在"底图 + 残差合成"之后？（FSR4 FG / XeFG 接入点审计）

> 2026-10-29 20:30　专项记录（回答"CoGPU 合成之后接 FSR4 FG 或 XEFG"）
> 前置文档：[帧生成-三形态对比](帧生成-三形态对比-20261027.md)（两种 FG 的资源需求 + 判据）
> 相关：[B形态-当前状态与交接](B形态-当前状态与交接-20261027.md)、[知识库 §十三](社区DLSS5-知识库-20261026.md)、[假NGX 可做的事](待办-假NGX可做的事-20261029.md)
> 结论先行：**接得上，但"接在 B 形态的合成之后"是最别扭的位置；真正对的位置是 A 形态（A）或单卡（9070 XT）。**

---

## 0 · 一句话结论

```
库我们有、硬件我们有、代码里那个接点也清楚（v9 的 Stage2：合成 → 上采样 → Present）。
但两种 FG 都不是"给一张图就插一帧"的函数，而是【代理交换链 + 自己控 present】。
而 B 形态的 present 是"我们的合成交换链 + DComp 覆盖层"（没有 HWND，且跨适配器合成），
——这正是 FG 唯一不能忍的两件事。所以：
  · A 形态（合成在 A、present 在 A）：XeFG 可接，且是"合成之后"的字面位置
  · 单卡形态（都在 9070 XT）：FSR4 FG / XeFG 都能接，位置最正
  · B 形态（合成在 B、present 是我们的覆盖层）：技术上要改造出画层才行，性价比最低
```

## 1 · 接点在哪（代码事实）

| 事实 | 位置 |
|---|---|
| B 形态出画的完整链：**合成 → 上采样 → CopyResource 到后缓冲 → Present** | `ingame\libxess_proxy_v9.cpp:3172`（`BformPPStage2`）→ 合成 `:3181~3235` → 上采样 `:3237~3270` → 拷后缓冲 `:3272~3288` → **`g_bpSc->Present(0,0)` `:3293`** |
| bform=9（4K 后置）时合成输出本身就是 4K，后续不再放大 ⇒ **"合成之后"= 直接就是待出画帧** | `:904~906`、`:2787` |
| 每槽已经有 MV + 深度 + jitter（FG 的主要输入其实在手上） | `:1532`（注释："传合成后的 pColor + 该槽位的 MV + 深度 + jitter"）、`:1503`、`:1516` |
| 我们的 jitter 被缩放成 0.5 再交给 XeSS（与 FG 契约冲突，见 §4c） | `g_jitterScale = 0.5f` `:75`，使用处 `:4406`、`:4674` |
| B 的出画交换链是 `CreateSwapChainForComposition`（**没有 HWND**）+ DComp 视觉 + 缩放变换 | `:2921`、`:2938~2957` |
| A 形态的合成在 A 上做（`slot[presentFrame] + 残差 → pColor`） | `:4555` 附近 |

⇒ 用户问的那个点，物理上就是 `:3293` 之前。**位置不缺，缺的是"谁能拥有 Present"。**

## 2 · 两个候选 FG 的真实契约（2026-10-29 查证）

### 2.1 XeSS-FG（XEFG，Intel XeSS 2，`libxess_fg.dll`）

来源：[Intel XeSS-FG Developer Guide 1.3](https://raw.githubusercontent.com/intel/xess/main/doc/xess_fg_developer_guide_english.md)

```
★ 关键：Requirements 明写"or any non-Intel GPU supporting Shader Model 6.4" ⇒ RDNA 能跑（不是 Arc 专属）
★ 但："On non-Intel GPUs the maximum number of generated frames is one" ⇒ 非 Intel 卡最多 2X（MFG 8X 靠 patch）
· 形态：实现 IDXGISwapChain4 的代理交换链；xefgSwapChainD3D12InitFromSwapChain 会【释放】你给的交换链并重建
        （要求引用计数=1，独占全屏直接失败）；InitFromSwapChainDesc 需要【hwnd】
· 提交：插帧发生在你的 Present 内部，用你初始化时给的那条队列；非 Intel 卡由"高优先级后台线程 + 内部 DIRECT 队列"做节奏
· 必需输入：MOTION_VECTOR + DEPTH（tag）+ frame constants（view/proj 矩阵、jitter、MV scale、frameRenderTime、resetHistory）
  ＋ 每帧 Present 前必须 xefgSwapChainSetPresentId
· UI：默认"模型自己插 UI"；要干净得给 HUD-less + UI 两张图（组合模式）
· 硬依赖【XeLL】（低延迟库）：没有 XeLL context，代理交换链初始化直接失败；且"其他低延迟方案不支持"
· 明确不支持：第三方 FG 共存；同时多个代理交换链
· 本机 DLL 实测导出 29 个 xefgSwapChain*（含公开文档没写的 SetSceneChangeThreshold / SetParameterP / GetProfilingData）
```

### 2.2 FSR Frame Generation（`amd_fidelityfx_framegeneration_dx12.dll`）

来源：本地文件 + [AMD FSR SDK 2.x/Redstone](https://gpuopen.com/learn/welcome-amd-fsr-redstone-amd-fsr-sdk-21-available/)

```
· 本机是 4.0.1.2740（SDK 2.4.0 一档，40 MB —— 模型在库里，即 ML FG / Redstone 那条线）
· 同样是"present 接管"模型：交换链 + 节奏由库统筹，应用按帧提交 FFX 的 frame-gen 描述
· ML FG 首发绑 RDNA4（本地 `amdxcffx64.dll v2.2.0.1328 - FSR 4.1「Win 仅限 RDNA4」` 目录名亦如此）
  ⇒ 7900 XT（RDNA3）上大概率只能退到 FSR 3.x FG（非 ML）；未验证
· 相对 XeFG 的好处：不强制 XeLL、2X/3X/4X 都可
· 相对 XeFG 的坏处：第三方接管的先例比 XeFG 少（OptiScaler 那边 XeFG 的解锁/节奏补丁已经打磨过一轮）
```

### 2.3 社区已经实现过"接在上采样/NR 输出之后"这件事

`RESIDENT EVIL 2 ...\OptiScaler.ini` 的 `[FrameGen]` 段（本机文件，2026-10-26 现场）：

```
FGInput  = auto | dlssg | nvngxfg | fsrfg | 【upscaler】| fsrfg30 | nofg
   upscaler - Requires an upscaler, or final-image NR (PresentWithoutUpscaler) with XeFG.
              To prevent UI glitching, Hudfix is required
FGOutput = auto | 【fsrfg】(需 amd_fidelityfx_framegeneration_dx12.dll，FSRFG 3 或 4) | 【xefg】(需 libxess_fg + libxell) | dlssg
```

⇒ "**FG 吃上采样器的输出**"就是社区现成的 `FGInput=upscaler`；而"final-image NR + XeFG"（`PresentWithoutUpscaler`）
正是"只在最终图上做 NR，然后再插帧"的形态 —— 结构上和我们 bform=9 想做的事几乎一样。
**本机还有跑过的证据**（`OptiScaler.log` 2026-10-26 06:43）：

```
XeFGProxy::InitXeFG Loaded from ...\OptiScaler\libxess_fg.dll
XeFGUnlock::Apply 5 of 5 patches applied (0 skipped), MFG enabled up to 8X
XeFGPacing::Install generated frames are paced above 2X (thunk ...)   ← 连"2X 以上的节奏"都被补过了
```

⇒ **不是"能不能跑"的问题，是"挂在哪条交换链上"的问题。**

## 3 · 三形态 × 两种 FG：能不能挂、挂在哪（本次审计的核心表）

| 形态 | 合成在哪 | present 归谁 | FSR4 FG(ML) | XEFG | 评价 |
|---|---|---|---|---|---|
| **A 形态**（bform=0） | **A（7900 XT）** | 游戏（A 的窗口链，我们只在 XeSS 调用里） | ❌ 硬件大概率不满足（RDNA3） | ✅ **可挂**（FG 输入=合成后的 4K，MV/深度同卡同帧） | **"合成之后"的字面位置**；代价 = A 已经 305W/91% |
| **B 形态**（bform=6/9） | **B（9070 XT）** | **我们的合成交换链 + DComp 覆盖层** | ⚠️ 硬件满足，但 present 是覆盖层 | ⚠️ 需 HWND 链；覆盖层破坏节奏 | 要改造出画层才谈得上 |
| **单卡**（游戏+NR 都在 9070 XT） | 9070 XT | 游戏 | ✅ **最优**（RDNA4 + G-buffer 同卡 + 零搬运） | ✅ 可挂 | 20261027 文档早就点的"理论最佳" |

**为什么 B 形态最别扭**（三条结构性冲突，逐条有出处）：

1. **XeFG 只认 HWND 交换链**：`InitFromSwapChain` 会释放并重建你给的链（要求引用计数=1），`InitFromSwapChainDesc` 要 `hwnd`。
   我们的链是 `CreateSwapChainForComposition`（`:2921`），没有窗口 ⇒ 只能改走"自建置顶穿透窗口 + `CreateSwapChainForHwnd`"（这段代码本来就有：`MIR 方式 2`，`:5174`）。
2. **节奏会被跨适配器合成打散**：XeFG 在非 Intel 卡上靠"高优先级线程按显示节奏提 present"；而我们的画面最终是 **DComp 视觉贴到另一张卡的窗口上**，由 DWM 跨适配器合成。
   插帧的"deadline"在这一层不再成立 —— 典型表现就是抖/漏帧，而我们恰恰是靠"17.1ms 出画、双缓冲流水"撑 60fps 的。
3. **一个位置两个主人**：XeFG 明写"不支持第三方 FG 共存 / 不支持同时多个代理交换链"，而我们的 DComp 覆盖层+合成链本身就是第三个 present 参与者。

## 4 · 数据契约逐条对账（这决定"接上去了画质会不会崩"）

| 项 | FG 要什么 | 我们有什么 | 缺口/风险 |
|---|---|---|---|
| 色 | 当前帧 + 上一帧（全后处理、无 UI 更好） | ✅ 每帧 4K 成品（`g_bComp`/`ppUp4k`） | 我们的成品 **HUD 已烤进去，NR 残差也作用在 UI 上** |
| MV | 渲染分辨率像素单位；未去抖动；不 dilate（低分辨率 MV 由库自己上采样+dilate） | ✅ 每槽的 1080p MV（`:1503`/`:1532`） | 语义要核对（是不是已含 jitter、正负号）；我们还会把 jitter 缩到 0.5 再喂 XeSS（`:75`）——**这条与 FG 契约冲突，必须恢复 1.0 或单独给 FG 一份** |
| 深度 | 任意格式，尺寸与 MV 相同，可 inverted | ✅ 每槽深度已跨卡传 | 需给 FG 打上 `INVERTED_DEPTH` 之类的标志 |
| jitter / 矩阵 | frame constants 里要 view/proj（行主序、不含 jitter）+ jitterOffset + MV scale | ⚠️ jitter 有（`g_curJitX/Y` `:74`）；**相机矩阵没抓** | 传单位矩阵可行但画质打折（未验证） |
| UI | HUD-less + UI（组合模式），或让模型插 UI | ❌ 拿不到 UI 分离 | 默认插 UI ⇒ HUD 抖/拖 —— **这一项不比小黄鸭强** |
| 节奏 | 每帧固定 PresentId + 稳定帧时间 | ✅ 我们有固定 60 渲染节奏 | 但链路本身有 kDelay=3 的异步槽位 |
| **时域语义** | **假设"两帧之间只差 MV"** | ⚠️ NR 残差合成是**时域**的（状态纹理、预热 12 次、运动门控、alpha 混合） | **合成后的第 N 帧里带着 N-3 以前的时域内容**；FG 再按"N-1→N"插值，会把时域拖尾放大成"运动中双轮廓/残影" —— 正是六项检查的 A3/A5 |

> **这一条是最容易被忽略、也最可能就是翻车点的**：NR 是"让画面跨帧一致"，FG 是"按两帧差异造中间帧"。两者对"两帧之间差多少"的假设是相反的。要接，得让 FG 看到**没被 NR 时域处理过**的色（那就不是"合成之后"了），或者接受画质退化并逐项过六项检查。

## 5 · 帧时间账（决定"值不值得做"）

现有硬数据（[帧生成-三形态对比 §四](帧生成-三形态对比-20261027.md)、B 形态交接）：

```
B 卡 NR            network 12.0ms，占用 88%，功耗仅 130/304W
B 卡加 1/4 附加负载 NR 14.2 → 17.9ms（+26%）      ← NR 是【延迟受限】，任何抢 GPU 的活都直接变慢
60fps 定版天花板   16.67ms；B 出画实测 17.1ms（A 不等所以游戏仍是 60）
A + 小黄鸭         180 显示帧，0 行代码
```

FG 的时间要加在 **B 的 present 前**（串行同队列），而 B 的余量已经被 NR 吃掉：

| 方案 | 4K 插帧成本（估） | 后果 |
|---|---|---|
| FSR4 FG(ML) @4K on RDNA4 | 2~4ms（**未实测**） | B 的 NR 被挤 ⇒ 12 → 14~16ms，出画 17.1 → 19~21ms，破 60 |
| XeFG @4K on 非 Intel | 6~10ms（**未实测**，无 XMX 加速） | 直接不可用 |
| 小黄鸭（进程外） | 0（不在这条链上） | 已 180 帧 |

判据（沿用 20261027 §七）：**基准帧时间 + FG 时间 > 16.7ms ⇒ 该方案在 60 基准下不成立。**
⇒ B 形态下即便把交换链问题解决，**帧时间这一关先过不去**；除非先把 NR 压到 ≤10ms（换 Small 模型 / 降 NR 分辨率）。

## 6 · 结论与建议路径

### 6.1 直接回答"能不能接"

```
能接，但"合成之后"这句话在三个形态里指的是三个不同的地方：

· 想在【B 形态】接 → 不行得痛快：XeFG 要 HWND 链 + 独占 present + 自己的节奏，我们是 composition 链 + DComp 覆盖层；
  且 4K 插帧 2~10ms 加在已经 88% 负载的 B 上，必然破 60fps。
· 想在【A 形态】接 → 可行（XeFG 一条路；FSR4 ML FG 在 RDNA3 上大概率没有）：
  合成就在 A，MV/深度/色同卡同帧，挂在我们已有的 dxgi 层（dxgi_proxy_v4 的 vtable patch）或 OptiScaler 的 FGOutput=xefg。
· 想在【单卡】接 → 最优：FSR4 FG 与 XeFG 都成立，G-buffer 同卡、零搬运、一条窗口链。
```

### 6.2 推荐顺序（性价比）

```
第 0 步（0 成本，保留）：A + 小黄鸭 = 180 帧，继续当基线
第 1 步（半天，只做探针，不碰产线）：量"4K 插帧到底多少钱"
       独立 exe 载 libxess_fg(+libxell) / amd_fidelityfx_framegeneration_dx12：
       9070 XT 上 CreateContext → 自建窗口 4K 链 → 喂 07_素材与抓帧 里的真实合成帧 + 1080p MV/深度
       → 读 GetProfilingData / 帧时间；判据：≤2ms 才继续，>4ms 直接放弃
第 2 步（如果第 1 步过）：选形态
       优先"单卡形态 + FSR4 FG"（最短、最正）；次选"A 形态 + XeFG"（保留跨卡 NR）
       B 形态只在"必须保留 B 出画"时才做，且要先改造出画层（窗口链 + 节奏交还 FG）
第 3 步：接上之后按六项检查验，重点盯 A3 运动中双轮廓 / A5 拖尾（§4 的时域语义冲突）
```

### 6.3 明确不要做的事

```
· 不要在 B 的 composition 交换链上硬套 XeFG（InitFromSwapChain 会释放我们的链，DComp 覆盖层会失去内容）
· 不要把 jitter 缩放成 0.5 的那份 MV 直接给 FG（契约要求"未去抖动"）
· 不要指望"FG 顺手把 UI 也插好"（HUD-less 分离我们没有，这一项小黄鸭同病）
· 不要把 4K 60→120 当成主要收益（需要 4K120 输出链路；文档判据写的是"把 30~40 拉回 60~80"）
```
