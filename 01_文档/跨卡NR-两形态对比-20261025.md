## 一、职责对照

| | 游戏 | A（7900 XT） | B（9070 XT） |
|---|---|---|---|
| **原版** | 渲染 + **自己调 XeSS 上采样** + **自己 present** | 捕获 → 降 1080p → 跨卡 → 等答案 → 残差合成进 pColor → 调真 XeSS(jitter×0.5) | 只做 NR（14ms） |
| **新形态** | 渲染（XeSS 可调可不调） | 捕获 → 跨卡（color+MV） | **NR + 上采样 + present** |

**关键结构差异一句话：原版把上采样留在 A，正好和 B 的推理并行；新形态把上采样挪到 B，于是两件事在 B 上串行。**

新形态的数据流：

```
A（7900 XT）                          跨卡单向                    B（9070 XT，显示器接这里）
游戏渲染 2227×1253（含HUD）                                    ↓
  ├ color  11.16 MB  ──────────────►  22~34 MB/帧   ──►  降到1080p → NR（lmxxf/mochizuki）
  ├ MV     11.16 MB（2ch R16G16F）                        → 残差抬回 2227×1253
  └ depth  11.55 MB（仅当上采样器要）                     → 上采样 2227×1253 → 4K（FSR4）
                                                          → B 自己 present（全屏 flip）
游戏自己的 XeSS 可以不调（省 2~4ms，pOutput 作废，被盖住）
```

## 二、五个维度逐项比

### 1. 跨卡流量

| | 每帧 | 60fps | 120fps |
|---|---|---|---|
| 原版（1080p 色出 + 1080p 答案回，不含 MV） | **16.6 MB** | 1.0 GB/s | 2.0 |
| 原版 + 若把 MV 也送（1080p 2ch） | 24.9 MB | 1.5 | 3.0 |
| 新形态（原生色 + MV 2ch） | 22.3 MB | 1.3 | 2.7 |
| 新形态（原生色 + MV + depth 给 FSR4） | 33.9 MB | 2.0 | 4.1 |

**结论：差距的本质不是“残差省、整帧贵”，而是底图在谁手里。** 原版的全分辨率画面留在 A，跨卡只运“网络分辨率的两张图”（1080p 色出去 + 1080p 答案回来，残差是在 A 本地用 `答案 − 喂入` 算出来的，它本身不过卡）；新形态因为 B 要负责上采样和出画，**底图必须过到 B**。两个形态**都不搬 4K**，真实差距是 16.6 → 22.3MB（1.35 倍），且新形态多出来的部分里一半以上是 MV——那是原版压根没付的开销。

逐字节拆账：

```
新形态 22.32 − 原版 16.59 = +5.73MB
  ├ 色彩从 1080p 提到原生：11.16 − 8.29 = +2.87MB   ← 分辨率代价
  ├ MV 原版根本没送：            +11.16MB             ← 新增的输入
  └ 省掉回程：                   −8.29MB              ← 单向的好处
```

> 关于“残差是否包含原画面每个像素”：残差场确实是整幅的（2227×1253 每像素一个值），
> 但它是 `答案 − 喂入网络的那张图`，**底图 `pColor` 从未上过总线**。
> 残差能小，不是因为它稀疏，而是因为**底图在本地，一个字节都不用搬**。

### 2. 延迟

| | 屏幕上显示的是第几帧 | 修正来自第几帧 | 端到端延迟 |
|---|---|---|---|
| **原版** | **N−3 的原始帧** | **同一帧 N−3 的修正** | **3 帧**，60fps ≈ **50ms** |
| **新形态** | N | N（同帧配对） | render→present 插入 copy + NR + 上采样 ≈ **16~18ms ≈ 1 帧**（lmxxf）／ 6~9ms（mochizuki） |

- **原版是“配对但滞后”**：修正和帧是同一帧，没有错位；代价是整帧被推迟 3 帧。这也正好解释为什么 `kDelay` 必须 ≥3（`(kDelay-1)×帧时间 > worker 时间 + 2ms`）——它本质上是**用帧延迟换配对**：游戏的 present 不接受等待，本帧等不到自己的答案，只能拿 3 帧前的槽位来配。
- **新形态是“配对且只滞后 1 帧”**：present 在自己手里，可以等本帧的 NR 结果再上屏，所以 1 帧就够。
- **结论：延迟这一项新形态反超，约省 2 帧（≈33ms @60fps）。原版的 3 帧是实打实的输入延迟，不是错位。**

### 3. 吞吐（决定性）

| | A 每帧成本 | B 每帧成本 | 帧率上限 |
|---|---|---|---|
| 原版 + lmxxf | ~11ms（提交 10.8~12.4） | 13.2~14.3ms | **≈71fps（B 卡瓶颈）** |
| 新形态 + lmxxf | ~4~5ms | **14 + 2~4 = 16~18ms** | **≈55~60fps** |
| 原版 + mochizuki | ~11ms | ~4ms | **≈90fps（A 卡瓶颈）** |
| 新形态 + mochizuki | ~4~5ms | **4 + 2~4 = 6~9ms** | **≈110~160fps** |

**这是整份对比里最重要的一行：用 lmxxf 时，新形态比原版慢（55~60 vs 71fps）。** 因为原来上采样是“免费”的（在 A 上与 B 的推理并行），现在变成了 B 的串行成本。只有换上 mochizuki，新形态才反超，并且反超得很明显。

> ⚠ **本段前提已被推翻**：这一整段假设“B 为瓶颈”。§3.5 的驱动读数显示 B 只有 70%、真正的瓶颈是 A，
> 所以 lmxxf 下两者吞吐**基本持平**（≈50fps），不是新形态降级。见 §3.5 第 4 条。

**另一个直接后果：B 的吞吐 = 显示帧率上限。** B 追不上游戏时只能重复上一帧 → 周期性卡顿，所以要么把游戏限帧到 B 的吞吐，要么做帧重复策略。

### 4. 画质

| | 原版 | 新形态 |
|---|---|---|
| 上采样器 | 游戏内 XeSS 2.0.2.68，跑在 **RDNA3** | **FSR4，跑在 RDNA4**（硬件更强） |
| jitter | 被迫 `×0.5` 迁就游戏（代价：略软、HUD 闪） | 自己定，不用妥协 |
| 残差落点 | pColor 网格 2227×1253，然后被 XeSS 一起上采样 | 2227×1253，然后被 FSR4 上采样 |
| 修正时序 | 配对，但整帧滞后 3 帧 | 配对，滞后 1 帧 |
| depth | 目前惰性，没参与 | 可正式喂给上采样器 |

**结论：新形态的画质上限更高**（更好的上采样器 + 无 jitter 妥协 + 滞后更短），但前提是 FSR4 集成到位；换成双线性就直接出局。

> 附注：`省带宽` 与 `画质` 在这里是耦合的——时域上采样器（FSR4/XeSS）都要吃 depth，
> 一旦要 4K 细节，depth 这份钱（11.55MB）就得付；不吃 depth 的纯空间放大才真省，但画质出局。

### 5. 工程、风险、回退

| | 原版 | 新形态 |
|---|---|---|
| 新增要写的 | 无（已跑通） | 上采样契约（color/MV/depth/jitter/exposure）+ 全屏 flip 出画 + 帧节拍 |
| 会话窗口模式 | 独占全屏可用 | **只能无边框**（叠加层前提） |
| 会不会丢游戏后处理 | **不丢**（游戏自己 present） | **pColor 之后的全丢**（RE2 的 HUD 在 pColor 里，需验证） |
| 前置配置 | 无 | **显示器物理接到 9070 XT**，GPU 偏好重设 |
| 失效后果 | 有天然兜底：链路没就绪就照常调真 XeSS，“最坏只是没有 NR” | B 挂了默认就是**黑屏/静止** |
| 兜底做法 | 内置 | 需自己造：**继续让 A 调真 XeSS**（浪费 2~4ms），B 失败就撤覆盖层退回游戏画面 |
| 撕裂风险 | 1080p 残差，有时域逻辑兜底 | 整帧 color，`无 fence` → 可见横缝 |
| 与现有代码复用 | — | 约 80%（捕获、跨卡契约、lmxxf 消费端、残差数学、调参全不动） |

## 三、双卡性能总开销

**口径**：每帧被“我们这个系统”占用的 GPU 时间，A 卡和 B 卡分别计；跨卡搬运走 K 槽错开、可与渲染/推理重叠，所以它是**占用上界**，不是关键路径。标注 `实测` 的来自日志，标 `*` 的是估算。

### 3.1 A 卡增量拆解

| 项 | 原版 | 新形态 |
|---|---|---|
| 等答案（有界 30ms） | 1.0~1.1（实测） | **0**（不需要） |
| 捕获 / 打包 | ~0.5* | ~0.5* |
| DownCS 2227×1253→1080p | ~0.3* | 不需要（直接送原生） |
| 跨卡写 | 8.29MB ≈ **2.0\*** | 22.3MB ≈ **4.5\*** |
| ResidCS 合成（2227×1253） | ~1.5* | **0**（搬到 B） |
| 真 XeSS 上采样 + jitter 替换 | ~3.0* | **0**（或保留作兜底：+3.0） |
| **A 合计** | **≈11.0（实测 10.8~12.4）** | **≈4.5~5.0**（留兜底则 7.5~8.0） |

### 3.2 B 卡增量拆解

| 项 | 原版 | 新形态 |
|---|---|---|
| 跨卡读 | 8.29MB（与推理重叠） | 22.3MB（与推理重叠） |
| 降到 1080p | 0（A 已降） | ~0.3* |
| NR（lmxxf / mochizuki） | 13.6~14.0（实测） / 3.3~4.7（实测） | 同左 |
| 残差抬回 + 合成 | 0（A 做） | ~0.5* |
| 4K 上采样 | 0（A 做） | **FSR4 ≈2~4\*** |
| present（flip） | 0（游戏做） | ~0.5* |
| **B 合计（lmxxf）** | **≈13.7（实测 13.2~14.3）** | **≈17~18** |
| **B 合计（mochizuki）** | **≈4.5\*** | **≈7~9** |

### 3.3 总账

| 形态 / 后端 | A | B | **合计 GPU·ms/帧** | **关键路径 max(A,B)** | 帧率上限 | 60fps 预算占用（A/B） | 120fps 预算占用（A/B） |
|---|---|---|---|---|---|---|---|
| 原版 + lmxxf | 11.0 | 13.7 | 24.7 | 13.7 | **73fps** | 66% / 82% | **133% / 165%（不可能）** |
| 新形态 + lmxxf | 4.5 | 17.5 | 22.0 | 17.5 | **57fps** | 27% / **105%（超）** | —— |
| 原版 + mochizuki | 11.0 | 4.5 | 15.5 | **11.0（A 成瓶颈）** | **91fps** | 66% / 27% | **133%（不可能）** |
| 新形态 + mochizuki | 4.5 | 8.0 | **12.5** | 8.0 | **125fps** | 27% / 48% | 54% / 96% |

### 3.4 四条结论

1. **总开销新形态更低（24.7 → 22.0，mochizuki 下 15.5 → 12.5），但关键路径更长（13.7 → 17.5）。** 省下来的是重复劳动：原版 A 要“合成 + 上采样”，B 又算了同一份 edit；新形态把这两步合成 B 上的一次处理。多出来的是并行度——原版 A 和 B 的活是重叠的，帧率由 `max` 决定；新形态 B 内部是串行的，由 `sum` 决定。
2. **原版被自己的 A 侧锁死在 ~91fps。** A 的 11ms 里有一半是“等答案 + 合成 + 上采样”这种固定开销，换多快的后端都掉不下来。**所以原版在 120fps 上根本没有门票**（A 侧 133% 超预算）。新形态把 A 侧压到 4.5ms，天花板交给 B —— 想上高刷，**只能走新形态**。
3. **唯一“总开销低 + 关键路径也低”的组合是新形态 + mochizuki（12.5 / 8.0）。** 这也是为什么前面反复说：新形态的价值和换后端是同一件事的两半。
4. **A 被释放出来的 ~6.5ms 是隐性收益**：可以拿去跑录屏编码 / 物理 / 更高渲染分辨率，或者干脆让它把帧率顶到 120 再交给 B 做节流。原版没有这份余量。

> 提醒：3.1/3.2 里带 `*` 的项是按搬运量推的估算（跨卡按 2~5 GB/s 有效带宽、FSR4 按 RDNA4 4K 上采样 2~4ms）。这两个数一旦实测出来，整张总账会跟着变——尤其是 FSR4 和 22.3MB 单向搬运。
> 已有对照组：MGPU 搬同样的 33MB 量级时实测 `lat = 18~80ms`（折 1.8~0.4 GB/s），并与它自己的 25.6 / 32~41fps 对得上——**那条链路目前是瓶颈，不是推理**。

### 3.5 双卡占用（驱动读数，2026-10-26）

> **口径变更**：本机 Windows 侧的 GPU 计数器**不可信**（任务管理器 / WMI / PDH 在 9070 XT 上与驱动读数不符，
> 疑与显卡保活的 OpenCL 烧机有关——该脚本自己也注明“OpenCL 计算在 Windows 计数器里看不到”）。
> 曾用 WMI 采到的那组（A 73.4% / B compute≈100%）**作废**，本节只用 **AMD 驱动面板读数**。

会话状态：`pColor 2560×1440 → 4K`；`worker 13.7~14.5ms`；`提交 11.2~11.9ms`；`合成=1`

| | **A · 7900 XT** | **B · 9070 XT** |
|---|---|---|
| GPU 占用（驱动，**整卡**） | **85~90%** | **≈70%** |
| 板功耗（**整卡**） | **≈305 W** | **180~240 W（波动）** |
| 其中非游戏任务 | **≈10% / ≈80 W**（其他程序也跑在 A 上） | ≈0（纯 NR worker） |
| **RE2 自身** | **≈75~80% / ≈225 W** | **≈70% / 180~240 W** |
| 出厂 TBP | 315 W | 304 W |
| RE2 自身折载 | 225/315 ≈ **71%** | 180~240/304 ≈ **59~79%** |

**五条读数**：

1. **当前瓶颈是 A，不是 B。** 整卡 85~90%，扣掉别人的 ≈10%，我们这条链已占 75~80%；
   A 只剩 **10~15 点**余量，而这 10 点里还有约 2ms/帧 本来就不属于我们。
   ⇒ §3.4 #2“原版被 A 侧锁死”有了实证。
2. **B 还有约 30% 余量。** 由 `worker 14ms ÷ 70%` 反推帧周期 ≈ **20ms ≈ 50fps**；
   A 在这 20ms 里忙 ≈ 87.5% × 20ms ≈ **17.5ms**（其中 ≈2ms 是别的程序，游戏相关 ≈15.5ms）。
   （这只是推论，用实际 fps 一对就能验证。）
3. **B 的余量是“没活干”，不是“干活快”。** 帧率由 A / CPU 决定，B 每帧有约 6ms 在等。
   ⇒ 新形态把 FSR4（2~4ms）加进 B，**占用的是这段空闲**，帧率代价接近于零：
   B 会从 70% 升到 **85~90%**，刚好与 A 持平。
4. **结论修正（重要）**：§二.3 / §3.3 / §四#3 里“新形态 lmxxf 下 55~60fps、比原版 71fps 降级”的
   前提是 **B 为瓶颈**。按驱动读数，B 只有 70%、真正的限制是 A，所以这个“降级”**不成立**——
   lmxxf 下两者吞吐基本持平（都在 ≈50fps 附近），新形态的收益（少 2 帧延迟、A 被释放）照旧成立。
   mochizuki 的价值也从“让新形态成立”降级为“把 50fps 的天花板抬到 110fps+”。
5. **粗算：新形态实际能拿到多少** —— 把 4.5ms 从 A 挪走 ⇒ A 掉到 ≈50%（含别人的 ≈2ms），天花板让给 B；
   B 加上 FSR4 后 ≈17ms ⇒ 帧周期可压到 **≈17ms ≈ 59fps**，比现在 ≈50fps 高约 **18%**。
   再上 mochizuki（B ≈7ms）⇒ 又轮到 A 变瓶颈，天花板约 **80fps 上下**（取决于 A 侧游戏渲染那 15.5ms 能降多少）。

> 附：§3.3 那四行的“帧率上限”是按**关键路径**算的理论上限，实际帧率由 A 与 CPU 决定（本机 ≈50fps），
> 不要把 73 / 57 / 91 / 125 当成当前能跑到的数字。

## 四、三个反直觉的结论

1. **带宽不是新形态的优势，基本打平。** 原版 16.6MB（因为底图留在 A），新形态 22.3MB（底图过卡）。差额主要来自“原生分辨率 + 新增的 MV”，而 MV 是原版从没付过的钱——公平对比（原版也送 MV）是 24.9 vs 22.3，**新形态反而更少**。
2. **延迟上原版吃亏，而且是它自己的架构性代价。** 3 帧（≈50ms）vs 新形态 1 帧（≈17ms）。原版拿 3 帧延迟去换“残差与帧配对”（游戏的 present 不接受等待，只能配 3 帧前的帧）；新形态因为自己 present，配对只需 1 帧。**这是新形态最实在的一项收益。**
3. **用 lmxxf 时，新形态是原版的降级**（55~60fps vs 71fps）。它的吞吐收益全部押在 mochizuki 上——那不是配套优化，是**同一件事的另一半**。
   > ⚠ **已修正**：这句的前提是 B 饱和。§3.5 的驱动读数是 A 85~90% / B ≈70% ⇒ 瓶颈在 A，
   > lmxxf 下两者吞吐持平；mochizuki 的作用从“让新形态成立”降级为“把 ≈50fps 的天花板抬到 110fps+”。

## 五、怎么选

| 你的目标 | 选哪个 |
|---|---|
| 现在就要能玩、随时能回滚、不想动显示器和桌面 | **原版**（它已经是可交付状态） |
| 想要更高画质上限、更低延迟、彻底摆脱游戏上采样器、准备换 mochizuki | **新形态** |
| 只是想把 NR 跑起来 | 原版；不值得为此重做显示管线 |
| 想冲 120fps / 想长期把 A 当纯渲染节点、B 当显示协处理器 | 新形态，且**必须和 mochizuki 一起立项** |

**最务实的路径不是二选一，而是让两者共存**：共用捕获、跨卡契约、lmxxf 消费端、残差数学（这 80% 是同一套），只把“上采样 + 出画”抽成一个可切换的后端（`游戏内 XeSS 上采样 + 游戏 present` / `B 上 FSR4 + B present`）。这样原版永远是可交付的底线，新形态是一个能随时 A/B 的实验分支——而不是一次不可回退的迁移。

## 六、开工前必须量三个数

1. **22~34MB 单向跨卡的有效 GB/s + p99 帧间隔抖动**（决定能不能压进 14ms）。
2. **B 上 `NR + FSR4` 的合计 ms**（决定帧率上限，也是 lmxxf / mochizuki 的裁决点）。
3. **RE2 在 pColor 之后还剩什么后处理**（决定画面会不会缺东西）。

三个数出来之后，原版 / 新形态 / 拓扑选择基本就自动分出胜负。

---

## 七、一句话

**原版把上采样放在 A，让两张卡真正并行，因此用 lmxxf 反而更快、总开销也更高（因为干了重复活），但代价是 3 帧的架构性延迟和 A 侧 11ms 的死开销（锁死 ~91fps）；新形态把上采样收到 B，带宽基本打平、总开销更低，但关键路径更长、吞吐更低，换来的是少 2 帧延迟、更高画质上限，以及一个能冲 120fps 的天花板。** 它换来的核心只有一件事：**B 从“NR 协处理器”升级成“显示协处理器”——延迟、画质、高刷是这件事的红利，吞吐是它的账单。** 只要 mochizuki 不到位，这笔账就是负的。

> ⚠ **据 §3.5 修正**：驱动读数是 A 85~90% / B ≈70% ⇒ 瓶颈在 A。所以上面的“吞吐更低 / 这笔账是负的”
> 在 **lmxxf 下不成立**（两者 ≈50fps 持平）；新形态真正的收益是**少 2 帧延迟 + 把 A 从瓶颈上摘下来**，
> 而 mochizuki 决定的是能不能把这 50fps 的天花板抬到 110fps+。
