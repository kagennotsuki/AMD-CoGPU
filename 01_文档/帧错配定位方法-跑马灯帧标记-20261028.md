# 帧错配定位方法：用「跑马灯帧标记」查出链路上哪个环节用了不同帧的内容

> 建立：2026-10-28（RE4 双 A 卡 MGPU 跨卡 NR 调试实战总结）
> 适用范围：任何「多帧数据在链路上流动、最终被合成」的管线 —— 神经渲染 / 超分 / 时域降噪 / 后处理搬卡
> 目的：**确定错配发生在链路的哪一段**，而不是靠"画质看起来如何"猜。

---

## 一、要解决的问题

合成公式（本项目实例）：

```
输出 = 底图 + （答案 − 喂入）× 强度
        │        └──── 一对 ────┘
        └── 残差
```

只要参与运算的两个量**不是同一帧的内容**，就会产生肉眼可见的错位（双轮廓、残影、拖尾），而且：

- 强度越大越明显；
- 静止时几乎看不出（两帧内容接近）；
- 运动时非常明显；
- **所有"健康指标"（帧率、等待时间、成功计数）都可能正常**，数值抓不到。

错配只可能发生在以下三个接缝之一：

| 编号 | 接缝 | 含义 |
|---|---|---|
| **A** | 答案 ↔ 喂入 | 网络交回的答案不是喂进去那一帧的响应 |
| **B** | 底图 ↔ 残差 | 用来相加的底图与残差不是同一帧 |
| **C** | 我们之外 | 上游/下游（如桥接层、呈现层）又叠了一层别的帧 |

方法的目标：**把 A、B、C 逐一排除**。

---

## 二、核心手法：埋一条"跑马灯"式帧标记

### 2.1 把画面想成一排 4 个停车位

```
┌────┬────┬────┬────┐
│ 1  │ 2  │ 3  │ 4  │   白底，只有一格停着"黑车"
└────┴────┴────┴────┘
```

**每一帧，黑车往右挪一格；挪出第 4 格后，下一帧回到第 1 格。**

```
第 0 帧   ■□□□
第 1 帧   □■□□
第 2 帧   □□■□
第 3 帧   □□□■
第 4 帧   ■□□□   ← 转回来
```

视觉上：**一条 1/4 屏宽的黑竖条，在纯白背景上匀速向右跑**，跑出去再从左边进来（跑马灯）。
其数学含义：**黑条位置 = 帧号 % 4**，即帧号被编码进了画面内容。

### 2.2 关键规则：同一帧的两张图，黑车必须停在同一格

```
喂入图（交给网络的）   □□■□   ← 第 2 帧，车在 3 号位
同帧底图（输出尺寸）   □□■□   ← 必须也是 3 号位
```

这两张图本来是同一帧拍下来的，标记理应一模一样。**只要链路没有错帧，它们就永远同步。**

### 2.3 于是"相减"变成一句很朴素的话

```
黑车位置一样   →  0−0 = 0，1−1 = 0   →  相减结果【干净的中灰，什么痕迹都没有】
黑车错开       →  0−1 = −1（黑块）／1−0 = +1（白块） →  【有格子花掉了】
```

> **一对图拍在一起，黑车对得上就什么都不留；错开才会留下痕迹。**

### 2.4 三条铁律

1. 标记必须**画在数据里**（喂入图 / 底图），**不能**画在屏幕上现成的图上——否则自己污染自己的判断；
2. **整块、满高、1/4 宽**——网络再怎么处理也抹不掉（且不能靠"哪边更亮"来判断，因为网络会做亮度归一，用"哪一格是黑的"这种位置编码才稳）；
3. **逐帧变相位**——否则无法判断"这是哪一帧的"。

## 三、画面分成上中下三层，分别展示什么

开启调试视图（本项目 `DebugView=13`）后，屏幕被切成三条等高横带，**每条带装的是同一帧（被呈现的那一格）里的一个环节**：

```
┌────────────────────────────────────┐
│ 上 1/3：答案                        │  网络交回来的那张图（放大到输出尺寸）
│        "网络看到什么 + 改了什么"      │  → 确认网络确实收到标记、并把它带回来了
├────────────────────────────────────┤
│ 中 1/3：残差                        │  答案 − 喂入，中灰代表 0
│        "网络到底改了什么"            │  → 判断"答案与喂入是否同帧"（接缝 A）
├────────────────────────────────────┤
│ 下 1/3：合成                        │  槽里的输出尺寸底图 + 残差 × 强度
│        "最终上屏的那张图"            │  → 判断"底图与残差是否同帧"（接缝 B）
└────────────────────────────────────┘
```

**为什么必须三层并排**：错配可能发生在两个不同的接缝上。只把三个量同时摆在眼前，才能一眼看出是"哪一条接缝"错，而不是只能得出"画面不对"。

## 四、判读规则

### 4.1 残差（中条）

| 相位差 | 中条长什么样 |
|---|---|
| **0（同帧）** | 两个标记完全重合 → 相减 ≈ 0 → **均匀中灰，看不到图案** |
| **1 帧** | 相邻两格：一格**黑**、一格**白** |
| **2 帧** | 相隔一格的两格：一格**黑**、一格**白** |
| **3 帧** | 仍是相邻两格，但黑白方向与"差 1 帧"相反 |

### 4.2 合成（下条）

| 情况 | 下条长什么样 |
|---|---|
| 底图与残差同相位 | 黑条**匀速一格一格右移** |
| 底图比残差新一帧 | 黑条位置**比应有的靠右一格**（看起来"跳了一格"） |

### 4.3 定位逻辑

| 观察 | 结论 |
|---|---|
| 中条出现黑块／白块 | **A 错**：答案与喂入不同帧 |
| 中条均匀灰，但下条黑条比上条靠右一格 | **B 错**：底图比残差新一帧 |
| 下条与上条同相位 | A、B 都对 → 只剩 **C**（上游/呈现层） |

## 五、执行纪律（每一步都必须能自证）

1. **先证明标记能被看见**
   单独做一个"只显示底图"的开关（本项目 `DebugView=11`），确认"槽里的输出尺寸底图真的被换成了黑白条"。
   *不要跳过这一步*：否则你无法区分"标记没生效"和"错配不存在"。

2. **加计数器，区分"没调用"和"调用了但没生效"**
   例：`图案填充=4980` 说明替换动作每帧都在执行——此时若画面仍是原始内容，问题就在**数据流**而不是**调用**。

3. **用确定性实现，不要依赖"跑个 compute 写进去"**
   本项目踩过的坑：compute dispatch 每帧都执行（计数器在涨），但写入没有落到目标纹理。
   改为：**开机生成 4 张成品图（4 个相位各一张），每帧只做一次整图 `CopyResource`** —— 复制要么成功、要么报错，不存在"半成功"。

4. **提防静默钳制**
   参数解析里写死的范围会把设置**悄悄丢掉**，表现像"功能没做"：
   - `DebugView ≤ 3` → `DebugView=13` 被忽略；
   - `AnchorDelay ≤ 2` → `AnchorDelay=3` 被忽略。
   **凡是"我设了但没反应"，先查参数有没有被范围吃掉。**

5. **一次只改一处，改前备份，改后重建并校验产物**（大小 / 时间戳 / 特征字符串）。

## 六、实战案例：本项目抓到的真 bug

### 6.1 现象

`DebugView=13` 三横条读数：

```
上条（答案）  黑条在第 2 格
中条（残差）  均匀灰          ← 答案与喂入同帧，相减=0 ✓
下条（合成）  黑条在第 3 格    ← 底图的条比答案新一格 ✗
```

结论：**残差没问题，是"底图比残差新一帧"**（接缝 B）。

### 6.2 根因

同一个帧号在**两处被读出不同的值**：

```
P1 画喂入图案时     → 读 g.frame = N−1
之后 ++g.frame
写槽贴底图图案      → 读 g.frame = N
```

用跑马灯的话说：**同一帧的两张图，被贴了相隔一格的两张标记**

```
喂入图   □□■□   ← 车在 3 号位
底 图   □□□■   ← 车在 4 号位
```

### 6.3 修法

**帧号在消费端入口处自增一次**，整帧只用这一个值（`fi.frame_id` 不再自增）。

### 6.4 可推广的教训

> 一帧内所有"按帧计算"的量（相位、槽号、帧号、图案位置）**必须派生自同一个、只在帧首自增一次的帧号**。
> 不同阶段各读一次 `g.frame`，就一定会差一帧 —— 而且这种错**不会**体现在任何计数器上。

## 七、方法的最小结

```
① 拆成对 → ② 数据里埋帧号（跑马灯黑条） → ③ 相减使"对=0" → ④ 上中下三层并排定位 → ⑤ 每层先自证可见
```

它把"哪里错了"从"凭感觉看画质"变成"屏幕上有没有那块图案"，所以能一次定死责任落在哪一环。

## 八、本项目的具体开关（RE4 跨卡 NR 适配层）

| 位置 | 键 / 视图 | 作用 |
|---|---|---|
| `nvngx_tuning.ini` | `DebugView=0` | 正常画面 |
| 同上 | `DebugView=11` | 只显示"槽里的 4K 底图"（验证标记是否真的贴上了） |
| 同上 | `DebugView=13` | 上 1/3 答案 / 中 1/3 残差 / 下 1/3 合成 |
| 同上 | `AnchorDelay=`（0–5） | 呈现延迟（呈现第 N−k 帧那一格） |
| 同上 | `AnsOffset=0/1` | 答案取哪一格（0=与画面同格；1=后一格） |
| 日志 | `图案填充=` | 底图替换执行计数（区分"没调用"与"调用了没生效"） |
| 日志 | `Dv=` / `图案=` | 实际生效的视图号 / 图案开关值（确认参数没被钳掉） |

实现要点：4 张相位成品图在初始化时生成一次，之后每帧只做整图复制；三横条在合成着色器里按 `uv.y` 分区输出。

## 九、附：2026-10-28 RE4 适配层实测最佳档位

在修好"底图比残差新一帧"之后，用 `DebugView=0` + 逐档热键对比得到（用户目视判定）：

| 旋钮 | 最佳档 | 值 | 说明 |
|---|---|---|---|
| 残差模糊（`Ctrl+Alt+1`） | **白色块**（第 3 档） | `ResidBlur=2`（5×5） | 锐度损失可接受，边缘那条错位细线削得最干净 |
| 混合比例（`Ctrl+Alt+2`） | **最低档** | `ResidMixIdx=0`（混合 0.0） | 纯残差叠加优于任何混合比例（混合会整体发软） |
| 去饱和 | 默认 | `ResidSat=0.90` | 照抄 RE2 |
| 限幅 | 默认 | `ResidLimit=0.25` | 照抄 RE2；我们此前实际能到 2.0，是边缘过冲主因 |
| 边缘保护 | 默认 | `ResidEdge=1.0` | 照抄 RE2（`e /= 1 + edge·var·8`） |

结论：
- **残差必须低通后再叠加**（`ResidBlur=2`）——这是本环节最有效的一项；
- **不要用混合替代相加**（`ResidMixIdx=0`）——混合虽然不会产生硬边，但整幅变软，观感更差；
- 该组合已写入 `nvngx_tuning.ini` 与代码默认值。
