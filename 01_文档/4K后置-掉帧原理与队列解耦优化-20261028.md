# AMD CoGPU · 4K 后置形态：为什么会拖慢游戏帧数，以及怎么救回来

> 记录时间：2026-10-28 晚
> 对应形态：`bform=9`（A 卡真 XeSS 放大到 4K → 跨卡 → B 卡在 4K 上做 NR → B 卡 present）
> 对应版本：`03_版本冻结\B4K-20261028`（808,448 B，SHA256 前16 B05FFC377B637E4B）
> 详细排错过程：`B形态-当前状态与交接-20261027.md` §一.7 (14)~(20)

---

## 一、现象

做完 4K 后置形态后，画面质量明显变好，但**游戏自己掉帧**：

| | A 形态（bform=0） | 4K 后置（bform=9，未优化） |
|---|---|---|
| 游戏自己 fps | 60 | **45** |
| 一帧耗时 | 16.7 ms | 22.3 ms |

注意：**掉的是"游戏自己"的帧数**，不是 B 卡出画慢。B 卡只是 1:1 跟着游戏走。

---

## 二、原理：所有活儿都排在"游戏必须整体等待"的那张清单里

### 2.1 游戏一帧是怎么出画的

```
游戏的 GPU 活儿是按一张"清单"（命令列表）打包提交的：
   渲染场景 → 各种后处理 →【我们插进去的 XeSS 放大】→【我们塞进去的跨卡拷贝】→ 上屏
这一整张清单是【打包提交】的，上屏（Present）必须等整张清单全部执行完
```

**关键**：清单里任何一项变慢，整帧都被拖慢——GPU 不会"这一项我先不等"。

### 2.2 我们塞进去的那一项有多贵

```
为了在 B 卡上做 4K 降噪，必须把 A 卡"真 XeSS 放大好的 4K 图"整张送过去
一张 4K 8bit 图 = 33.2 MB，加运动矢量 8.3 MB = 41.5 MB / 帧
实测口径（可靠）：同一场景下，把这一项放进游戏队列后，一帧从 16.7 ms 变成 22.3 ms ⇒ 净增约 5.6 ms
（早期曾用"41.5MB ÷ 反推带宽"估成 ≈12ms；那个带宽是从帧时间差反推的、没有单独测量过，只作参考不作结论）
```

### 2.3 于是账单变成这样

```
游戏自己渲染 + 我们前处理 ≈ 16.7 ms（刚好 60fps）
把 41.5MB/帧 的跨卡拷贝塞进同一张清单 ⇒ 实测净增 ≈5.6 ms
⇒ 22.3 ms ⇒ 45 fps
```

**所以掉帧不是"显卡算不动"，而是"游戏在等我们把图搬过去"。**

### 2.4 一个通俗的比方

```
游戏是后厨，每 16.7 ms 出一道菜。
我们为了给隔壁餐厅（B 卡）也送一份，把"打包 + 送餐"塞进了后厨出菜的同一个流程里
⇒ 每道菜都要多等几毫秒才能端出来。
```

## 三、优化设计（三件事，缺一不可）

### 设计① 把"送餐"从后厨流程里拆出去 —— 用我们自己的 COPY 队列

```
以前：拷贝录在【游戏那张清单】上 → 游戏出画必须等它
现在：拷贝录在【我们自己的一条 COPY 队列】上 → 游戏出画完全不等

游戏清单里只剩：
   · 10bit → 8bit 格式转换  ≈0.2 ms
   · 运动矢量 8.3MB          ≈2.4 ms
⇒ 游戏帧时间从 22.3 ms 回到 ≈13 ms（被 60fps 上限挡住）
```

### 设计② 用"围栏 + 双缓冲"保证顺序（否则会拷到写了一半的图）

两条队列各跑各的，没有任何先后保证。要拷贝的那张 4K 图，是**游戏那张清单里刚算出来的**，
如果我们的拷贝队列跑太快，可能图还没写完就去拷 → 拷到"半张新半张旧"。

两把锁解决：

```
① 内部围栏：游戏提交完那张清单之后打一个"记号"（Signal）
   我们的拷贝队列等记号过了才动手（Wait）——纯 GPU 侧等待，不占 CPU
② 双缓冲：转成 8bit 的图准备两份（按帧号奇偶分）
   拷的是"上一帧那份"，它必然已经写完；这一帧那份可以放心被新内容覆盖
```

### 设计③ B 卡要等"图真的到齐了"再用

```
B 卡每轮要解码 A 送来的槽位，抢在拷贝完成前解码 → 又是半张图
解法：把"拷贝完成"用一把【跨卡共享围栏】告诉 B 卡
      B 卡解码前先等这把围栏（GPU 层面等待，不占 CPU）
      围栏必须带 D3D12_FENCE_FLAG_SHARED_CROSS_ADAPTER 标志，否则 B 卡根本打不开
```

### 配套：4 坑"待拷队列"（FIFO）

```
每帧登记一个"待拷任务"，每帧开头把"已满足条件的"逐个启动
⇒ 任何一帧都不会被下一帧覆盖（单坑版本会丢任务，导致某些槽位永远不更新）
```

## 四、成果

| 项 | 优化前 | 优化后 |
|---|---|---|
| 游戏队列上的额外工作 | **12 ms**（33.2MB 拷贝） | **2.6 ms**（转换 + 运动矢量） |
| 游戏帧率 | 45 fps | **60 fps** |
| B 卡出画间隔 | 19.5 ms | **17.1 ms** |
| 跨卡颜色拷贝 | 偶有漏帧 | **2101 次 / 2102 帧，跳过 0** |
| 画质 | 真 XeSS 4K + NR | **完全不变** |

---

## 五、一句话总结

```
"跨卡传一整张 4K 图"这件事本身很贵（≈12ms）。
贵不是问题；把贵的事塞进"游戏必须整体等待"的那张清单里才是问题。
解法 = 把它搬到自己的一条流水线上，再用两把围栏保证"顺序对、数据全"。

换句话说：我们并没有让传输变快，只是让"游戏不用等它"——这才是那 15fps 的来源。
```

## 六、这套思路可复用的地方

任何"要把大块数据搬到另一张卡/另一个进程，而且不能拖慢主渲染"的场景都适用：

```
① 先算清"这笔搬运多少钱"（字节数 ÷ 实测带宽），判断它值不值得离开主队列
② 主队列里只留"必须与主渲染严格排序"的最小工作量
③ 搬到独立队列后，一定要回答两件事：
   · 生产者什么时候写完？（→ 在生产者队列上 Signal 围栏）
   · 消费者什么时候可以读？（→ 消费者队列 Wait 那把围栏）
④ 双缓冲是消除"读写撞车"最便宜的手段（拷旧的、写新的）
⑤ 跨设备共享围栏别忘了平台要求的标志位（D3D12 需要 SHARED_CROSS_ADAPTER）
⑥ 任务队列要有多个坑位——单坑会被下一帧覆盖，表现为"某些槽位永远不更新"，
   而且现象很像别的问题（画面闪回旧内容），极易误判
```
