## 一、这是什么

**AMD CoGPU** 是一套「**双 AMD 显卡协同神经渲染**」管线：
一张卡专心跑游戏画面，另一张卡专心跑神经网络降噪，两块卡像一台机器那样分工。

在 Resident Evil 2 上跑通**两种形态**，游戏内热键随时切换，两者都是 60 fps：

| | **A 形态**（`bform=0`） | **B-4K 形态**（`bform=9`） |
|---|---|---|
| 上采样在哪 | 放大**之前**做 NR，再由游戏放大 | 先放大到 4K，再在 4K 上做 NR |
| NR 分辨率 | 1440p（= 游戏渲染分辨率） | 4K |
| 谁出画 | **游戏自己**（A 卡） | **B 卡**（DComp 叠在游戏窗口上层） |
| 底图是否跨卡 | **不跨**，只运网络分辨率的两张图 | 跨，4K 底图必须过到 B |
| UI / HUD 是否显示 | **正常**：游戏放大后照常叠加 | **会消失**：B 的底图取自超分输出，超分后才画的 UI 不在其中；而 B 自己上屏又盖住了游戏出画 |
| 算力 | 更省 | 更大 |
| 适合的游戏 | **更通用**，尤其「UI 在超分之后才覆盖」的作品 | UI 在超分之前就画进场景图的作品 |

### A 形态（`bform=0`）：NR 在放大之前做，游戏自己放大出画

**两卡每帧做的事（并列对照）**

```
A 卡 · RX 7900 XT（游戏队列 + 出画）           B 卡 · RX 9070 XT（降噪队列）
─────────────────────────────────────         ─────────────────────────────────────
1. 游戏渲染 1440p（含 HUD）
2. 降采样到网络档位，色彩走独立 COPY 队列 ───→  1. 等跨卡围栏 → 解码喂入图
   运动矢量同清单送出（都与游戏出画并行）        2. 喂 mochizuki 运行时 → 得到残差答案
   ⇒ 游戏出画不等这一步
3. 接回 B 的答案 ◄──────────────────────────    3. 答案按网络分辨率回传 A
4. 本地合成：底图 + 残差 × strength（α≈0.66）
   （答案是"降采样图"，先在 A 上换算回原尺寸）
5. 写回 pColor → 游戏自带的真 XeSS 放大到 4K → 游戏 present
```

**A 形态一句话**：**B 卡只当"降噪协处理器"，画面始终在 A 手上——底图不过总线，UI 在放大之后才叠上去，所以 HUD 完全不经过神经网络。**

### B-4K 形态（`bform=9`）：A 卡放大到 4K，B 卡在 4K 上降噪并出画

**两卡每帧做的事（并列对照）**

```
A 卡 · RX 7900 XT（游戏队列，必须快）        B 卡 · RX 9070 XT（降噪队列）
─────────────────────────────────────       ─────────────────────────────────────
1. 2K 渲染
2. 真 XeSS 放大到 4K（写进 pOutput）
3. 转成 8bit（10bit 不跨卡直传）
4. 【独立 COPY 队列】拷 8bit 4K 色彩
   33.2MB ──────────────────────────────→   1. 等跨卡围栏 → 解码出 4K 底图
   ⇒ 游戏出画不等这一步                       2. 4K → 1080p 降采样（喂网络的输入）
5. 同清单拷运动矢量 8.3MB ─────────────→     3. 喂 mochizuki 运行时 → 得到残差答案
   （深度平面一并拷，但当前未参与网络）（上一帧数据，独立队列，与第 3 步并行）
                                            4. 合成：4K 底图 + 残差（α≈0.66）
                                            5. 拷进 B 卡交换链 → Present
                                               （DComp 叠在游戏窗口上层）
```

**关于深度**：深度平面是「拷了但当前没参与计算」——已知结论是它喂不进 mochizuki 运行时
（详见 `06_交接包\深度信息-交接包`），现在只占带宽。

**B-4K 形态一句话**：**A 卡负责"把 4K 底图送过来"，B 卡负责"降采样喂网络 → 合成残差 → 自己上屏"，其中"合成上屏"总是比"网络计算"晚一帧，用两条队列叠在一起跑。**

**为什么能加速**：神经网络降噪（NR）非常吃算力。放进 A 卡的渲染队列会拖慢出画；
搬到 B 卡后，A 卡的帧时间回到纯游戏水平。

|---|---|

| 画质 | A 卡真 XeSS 4K 放大 + B 卡 4K 神经降噪 |

## 三、核心设计（三条）

```
① 槽位环（Slot Ring）
   6 个共享槽位轮转，每格带"面单"（帧号 + jitter）
   B 卡按面单配对，绝不把 A 的答案配到别的帧上

② 大块传输离开主队列
   33.2MB 彩色不走游戏命令列表，改走我方独立 COPY 队列
   用「内部围栏（游戏提交后打记号）」保证顺序，用双缓冲避免读写撞车
   ⇒ 游戏出画完全不等这笔传输

③ 跨卡共享围栏
   拷贝完成的信号通过 SHARED_CROSS_ADAPTER 围栏传给 B 卡
   B 卡在 GPU 层面等"数据真的到齐"再解码，不占 CPU、不撕裂
```

## 五、这一段踩过的六个真坑（都是隐蔽型）

```
① 33.2MB 拷贝录在游戏命令列表上        → 游戏 60→45fps
② 按 list 指针身份匹配"含转换的 list"    → 游戏提交的不是同一对象，永不触发
③ 建围栏的函数被"触发拷贝"才调用        → 逻辑死锁，整条链一条日志都没有
④ 跨卡共享围栏缺 SHARED_CROSS_ADAPTER  → B 卡根本打不开围栏
⑤ 待拷队列只有 1 个坑位                 → 部分槽位永远不更新
⑥ ★双缓冲纹理共用一个 UAV 描述符        → 一张从未被写入，画面逐帧闪回启动画面
```

**定位方法（可复用）**：把链路每个环节（A 发出 / B 收到 / B 合成）连续几帧的
画面抓下来，用「平均亮度 + 文件体积」量化对比。加载画面约 0.8MB/亮度 22.9，
游戏画面约 9.3MB/亮度 48 —— 一眼就能看出哪一环在交替。

## 七、边界与已知限制

```
· 跨卡传输很贵（实测：把 41.5MB/帧 放进游戏队列，帧时间净增约 5.6ms）
  ⇒ 传输量必须控制在"能藏在帧时间内"的水平，或干脆挪出游戏队列
· 目前只验证了 RE2（RE 引擎）；其它引擎需要重新确认上采样器注入点
· 帧生成（FG）路线已评估后取消；FSR4 路线取消（真 XeSS 已满足放大需求）
· bform=6（Catmull-Rom 2K 路径）已弃用，仅作应急回退
```

**组件归属与许可**

| 组件 | 归属 | 许可 |
|---|---|---|
| 跨卡代理 `libxess.dll` | AMD CoGPU 项目 | 我们自己的 |
| 神经降噪运行时与模型（`LmxxfNrRuntime.*`、`dlssnr-amd\`）| **mochizuki0323** | **MIT**（必须随附许可原文）|
| `libxess_orig.dll`（XeSS 运行库）| Intel Corporation | Intel XeSS SDK（不由我们分发）|

安装器会生成 `AMD-CoGPU-第三方组件声明.txt`（含 MIT 原文），并校验 `dlssnr-amd\LICENSE-DLSSNR-AMD.txt` 存在。
**运行时分发（方案 B：自托管壳版本 + 上游可追溯）**

```
我们代理的调用契约：LmxxfNrGetApi（ABI 表）+ LmxxfNrRuntime.pak（模型资产）
  实测：LmxxfNrRuntime.dll 与 MochizukiNrRuntime.dll 为同一份文件（同 SHA256），
        同一 DLL 同时导出 LmxxfNrGetApi 与 MochizukiNr* 接口，内含 CC_SMALL_FP8 / CC_SILVER_AARDWOLD
        ⇒ 它是"mochizuki 网络 + lmxxf 形态 ABI"的双兼容构建

上游 mochizuki0323/DLSSNR-AMD（MIT）：官方 Windows 包 = dlssnr-amd.asi + CC_* 模型 + 自家安装器
  ⇒ 不含 LmxxfNrRuntime.*，不能直接替换我们的运行时

所以：清单里同时写【上游地址（作者/许可/可追溯）】与【selfHosted 自托管包（安装器优先用）】
     安装器解压后检查 proxyRequires，缺文件就明确报"与代理不兼容"，不假装成功
```

## 九、已验证的游戏

| 游戏 | 自带 XeSS | 状态 | 实测 |
|---|---|---|---|
| Resident Evil 2 | 2.0.2.68 | ✅ 已装并验证 | 游戏 60fps / B 出画 17.1ms / 跨卡拷贝跳过 0 |
| Resident Evil 4 | 2.0.2.68 | ✅ 已装并验证 | B 出画 16.79ms / 跨卡拷贝 6901 次·跳过 0 / 提交 2.7~3.2ms |

**为什么同一套代理能同时用在两作**：两作自带的 Intel XeSS 都是 2.0.2.68，代理转发的正是这套 ABI。
**首次部署的关键一步**：安装器会把游戏自带的原版 XeSS 自动改名成 `libxess_orig.dll`，再把我们的代理装成 `libxess.dll`。

**一个真实陷阱（已用机制防住）**：测试机的 RX 7900 XT 被改名成了 "AMD Radeon RX 9070"。
如果按显卡名字选卡就会选错；我们的选卡只认 PCI DeviceId（0x7550 = 9070 XT），
日志里能看到 `worker 候选[0] = AMD Radeon RX 9070 DeviceId=0x744C` 与 `候选[1] = ...9070 XT DeviceId=0x7550` 被正确区分。
