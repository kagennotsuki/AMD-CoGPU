# 槽位队列（Slot Ring）：解决"原画面 ↔ 网络答案"错配的通用方案

> 来源：跨卡 NR 项目实战（RE2 × mochizuki × 双卡），2026-10-28 整理
> 对应版本：R1-20261026（`libxess.dll` 674,304 B）
> 适用场景：**异步**的画面增强 —— 把画面送出去算、算完再把结果贴回来，而游戏每帧都要出图

---

## 一、要解决的到底是什么问题

### 1.1 症状

```
· 画面错位 / 双轮廓（运动时物体边缘出现"两个"）
· 有时伴随残影、拖尾
· 而所有"健康指标"看上去全绿：合成=1、等待均值 0.8ms、超时 0 次
```

### 1.2 根因

网络（或任何异步处理器）是**流水线**，不是函数调用：

```
第 N 帧画面 ──送出去──> [网络 8~13 ms] ──> 第 N 帧的答案
游戏第 N 帧必须立刻 present，等不起这 13 ms
```

于是产生二选一的错觉：

| 做法 | 结果 |
|---|---|
| 用"当前画面 + 刚回来的答案" | 答案属于**更早的某一帧** ⇒ 配错帧 ⇒ **错位/双轮廓** |
| 等答案回来再 present | 每帧多等 10+ ms ⇒ 卡顿、掉帧 |

**真正的出路**：不要"用最新答案配当前画面"，而要**让画面和答案一起排队**——
第 N 帧的画面和第 N 帧的答案住在同一个"格子"里，只有这个格子同时具备两者时才拿它上屏。
这个格子就是**槽位（slot）**。

---

## 二、槽位队列的基本结构

### 2.1 一个槽位装什么

```c
struct Slot {
    // ① 该帧的输入（画面侧，必须原样保留到呈现那一刻）
    Texture2D color;      // 原始渲染图（我们的 2560×1440）
    Texture2D mv;         // 运动矢量
    Texture2D depth;      // 深度
    float     jx, jy;     // 该帧的 jitter
    int       frame;      // 这格属于第几帧  ★身份
    bool      captured;

    // ② 送进网络的降采样小图（残差基准）
    Texture2D fedTex;     // GPU 侧（1920×1080）
    uint8_t   feedInput[];// CPU 侧副本（算残差/静止检测用）

    // ③ 答案
    uint8_t   answer[];   // 1920×1080 网络输出
    int       answerFrame;// ★这份答案属于第几帧（身份校验）
    bool      hasAnswer;
};
```

**关键点**：三个"身份"字段（`frame` / `answerFrame` / 每槽独立的 `answer`）是整套方案的灵魂。
少了任何一个，就退回"用最新答案配当前画面"。

### 2.2 环形队列与三个下标

槽位数组大小 `K`，第 F 帧的槽位下标 = `F % K`。每一帧同时有三个角色（互相不能重合）：

```
第 N 帧：
  捕获  槽位 (N)       % K   ← 把本帧 color/MV/depth 拷进来
  喂出  槽位 (N − L)   % K   ← 把这一格的降采样小图送给网络（L = 喂帧滞后）
  呈现  槽位 (N − D)   % K   ← 用这一格的【画面 + 答案】合成后上屏（D = 呈现延迟 / kDelay）
```

- `L`（feed lag）：**数据通路决定**，不是自由参数（见第三节）
- `D`（kDelay）：我们可以调的
- 二者之差 `D − L` = **余量**：网络有多少帧的时间把答案交出来

### 2.3 一帧的完整流水（我们的实现）

```
① [CPU] 取答案：等 ansFrame[D%K] == 目标帧号（有界 30ms）；成功→拷贝到该槽；失败→本帧不合成
② [CPU] 回读上一轮降采样 → 填 feedInput → 交给 worker（inIndex, inFrame 一起交）
③ [GPU] 把本帧 color/MV/depth 拷进槽位 N%K，记录 jitter
④ [GPU] 降采样槽位 (N−1)%K → 1080p：→ 回读缓冲 / → fedTex / → 跨卡输入 buffer
⑤ [GPU] 合成：ResidCS(槽位画面, 上一槽画面, MV, fedTex, 答案, 时域状态) → 结果拷回 pColor
⑥ [转发] 调官方上采样器（MV/深度/jitter 换成被呈现槽位那一份）
```

> 注意 ②④ 的滞后是**错开的**：这一帧录的降采样，下一帧才读得到——这决定了 `L` 的真实值。

### 2.4 ★ 喂帧与取答案是**两条独立通道**（整套方案能非阻塞的关键）

上面 ① 和 ② 看起来都在"每帧必做"，但它们的**依赖关系完全不同**：

```
① 取答案：等的是"某一格的答案好了没"   → 有依赖，必须有界等待
② 喂帧  ：只等"喂入通道有没有空位"     → 不依赖答案，可以直接排队送出去
```

也就是说：**取答案不需要等喂帧完成，喂帧也不需要等答案取到**。两件事只是共用同一张槽位表。

```
时间轴（60fps，帧 16.7ms；网络 13ms）：
帧 N   ：① 取槽位 (N−D) 的答案（通常 0.9ms 就拿到）
         ② 把槽位 (N−L) 的小图推进"喂入队列" —— 推完就走，不等 worker 开始算
帧 N+1 ：worker 可能还在算上一份；游戏线程照常做 ①②③④⑤⑥
帧 N+2 ：worker 算完了 → 把答案放进它自己那一格（带帧号）
……
帧 N+D ：① 才真正用到那份答案
```

由此得到两个重要性质：

**性质 1：游戏线程每帧的耗时与 worker 的抖动解耦**
```
worker 快 → 答案早到，①的等待趋近 0
worker 慢 → ①等到超时（有界 30ms）→ 本帧不合成，但②照常喂帧
            ⇒ 下一帧、下下帧仍然正常出图（只是少了 NR 效果），不会卡死、不会连续崩
```

**性质 2：余量 `D − L` 的本质 = "允许 worker 落后几帧而不丢帧"**
```
D − L = 1 → worker 只允许慢 1 帧；慢了就丢这一格的 NR
D − L = 2 → 允许慢 2 帧
```
这就是为什么弱机应该调大余量：不是"网络变慢了"，而是**给队列更多缓冲位置**。

**实现上要小心的一点：喂入通道本身也是队列，深度决定"能不能排队"**

```
· 单 inbox（深度 1）：游戏线程喂帧时，若 worker 还没取走上一份 → 新帧会覆盖它 ⇒ 丢帧
                        （我们 R1 就是这个形态：Worker.inBuf 单份 + hasIn 标志）
· 环形喂入队列（深度 ≥ K）：每帧写自己的 input 槽，worker 按帧号顺序取
                        ⇒ worker 落后几帧也不丢输入，只是用完的时候更靠后
```

> 结论：**"喂"这一步的正确心智模型是"把帧塞进队列"，而不是"调用一个函数并等它返回"。**
> 只要喂入通道有空位，就直接塞；只有在通道满（队列深度不够）时才会被迫丢弃或阻塞。
> 详见第十节"已知改进点"。

## 三、硬约束的推导（把"感觉"变成公式）

### 3.1 答案什么时候可用

```
槽位 X 的答案最早可用时刻：
  第 (X + L) 帧  → 才送给网络
  第 (X + L + 1) 帧 → 答案才回来        （worker 周转按 1 帧算）
```

### 3.2 三条不变量

```
① 配对：第 N 帧呈现槽位 (N − D) 时，该槽的答案必须已经属于"同一帧"
        ⇒ N ≥ (N − D + L) + 1
        ⇒ ★ D ≥ L + 1

② 不撞捕获槽：D % K ≠ 0        （否则呈现的正是本帧刚写的格子）

③ 不撞喂出槽：D % K ≠ L        （否则呈现的正是网络此刻正在写的格子 → 撕裂）
```

合起来：**`L + 1 ≤ D ≤ K − 1`**，且 `D` 避开 `0` 与 `L`。

### 3.3 我们的真实数字

```
L = 2   （结构决定：降采样本帧录制、下一帧才能从回读缓冲读出）
K = 6   ⇒ D 可取 3 / 4 / 5  ⇒ 余量 = 1 / 2 / 3
```

`L` 为什么是 2 而不是 1：

```
我们已经把"第 N−2 帧的内容"降采样并读回（第 N−1 帧录、第 N 帧读）
若把标签写成 L=1 → worker 把答案写进槽位 (N−1)，而内容其实是 (N−2) 的
⇒ 内容一格、答案一格 ⇒ 错位，且等待均值仍然 0.8ms（数值抓不到）
```

这就是**为什么 L 不能靠改参数减小**：它是数据通路的物理事实，不是偏好。

## 四、余量的物理意义（决定画质/手感）

```
屏上内容延迟 ≈ D × 帧时间           （60fps 时 16.7 ms/帧）
可吸收抖动   ≈ (D − L) × 帧时间 − worker耗时
```

| 余量 | D | 屏上延迟 | 可吸收抖动（worker 12.7ms / 8.2ms） |
|---|---|---|---|
| 1 | 3 | ≈ 55 ms | ≈ 3 ms / 7.5 ms |
| 2 | 4 | ≈ 72 ms | ≈ 20 ms / 24 ms |
| 3 | 5 | ≈ 88 ms | ≈ 36 ms / 40 ms |

- **正常机器用余量 1**（延迟最低）
- **弱机 / 有后台负载 / 录屏**用余量 2~3：多一帧延迟，换 6~12 倍的抗抖
- 我们的实测：余量 1 时 `等待均值 0.9 ms`、`合成=1` 常驻、旧模型 network 12.4~12.6 ms

## 五、实现要点（每一条都对应一次真实故障）

### 5.1 答案必须按身份交付，不能用"最新到达"

```c
// ✗ 错误做法（我们踩过）：谁先到就用谁
if (worker.hasOut) { memcpy(slot[present % K].answer, worker.outBuf); }

// ✓ 正确做法：worker 每算完一格，把答案存进【那一格】并记下帧号
worker 完成格 i（内容属于 frameId）:
    memcpy(worker.ansBuf[i], worker.outBuf);
    worker.ansFrame[i] = frameId;

// 游戏侧：等到"属于我要呈现的那一帧"的答案
wait_until(worker.ansFrame[present % K] == presentFrame, timeout=30ms);
```

**为什么必须**：一旦改 K 或 D，相位就移动，"最新答案"与"要呈现的槽位"不再恰好相等，
于是每 K 帧就会错配一次 —— 表现为画面周期性抖动，而所有计数指标正常。

### 5.2 等待失败**绝对不能早退**（会自锁）

```
Execute() 的顺序是：① 取答案 → ② 喂帧 → ③ 捕获 → ④ 降采样 → ⑤ 合成 → ⑥ 上采样
```

若在 ① 失败时 `return 原函数(...)`，②的喂帧就被跳过 ⇒ worker 永远收不到新作业
⇒ 答案永远不更新 ⇒ ①永远失败。**自锁**（我们实测 NR 整体失效，日志里 worker 只跑过 1 个作业）。

```c
if (!got_answer) { slot.hasAnswer = false; /* 只影响合成 */ }
// 继续往下执行 —— 下面还有喂帧！
```

### 5.3 描述符槽位必须由 K 推导（K 一变就静默指错资源）

我们的映射（`K` 为槽位数）：

```
颜色      [0, K)
残差      K
netS      K+1        （UAV）
pre       K+2        （UAV）
smooth    K+3        （UAV，时域状态）
MV        [K+4, 2K+3)
fed       [2K+4, 3K+3)
答案      3K+4
堆大小    3K+5
```

**事故复盘**：旧代码把 4/5/6/7 写死给静态纹理，`K=4` 时颜色只用到 0~3 正好不撞；
`K=6` 时颜色占 0~5，其中 4、5 的 SRV 被残差/降采样目标覆盖 ⇒ 某些槽"读到的不是画面"，
表现为**画面在 4K 与低分辨率之间来回跳**。D3D12 不报错，只是静默指错。

### 5.4 其它必须记住的细节

```
· 答案 buffer：XHDR + K × (1920×1080×4)，每槽一段（共享内存跨卡时尤其重要）
· fed 纹理：每槽一份（残差 = 答案 − fed，必须同帧）
· 时域状态：独立一张 UAV；首次合成前显式清为中性 0.5，并预热若干帧
· 重建会话（换模型/换尺寸）：槽位、答案序号、时域状态全部按"新会话"重置
· 每槽内存账（我们的参数）：颜色 14.7 + MV 14.7 + 深度 14.7~18.4 + fedTex 8.3 +
  答案段 8.3 ≈ 61~64 MB 显存；answer + feedInput 两份 CPU 副本 ≈ 16.6 MB 内存
```

## 六、为什么不能更激进（把失败形态记下来）

| 尝试 | 现象 | 原因 |
|---|---|---|
| 只把 `D` 改成 2（`L` 仍 2） | 错位/双轮廓；等待均值仍 0.8ms | 呈现的格子答案还没生成（`D < L+1`） |
| 同时把 `L` 标签改成 1（`D=2`） | 由"错位"变成"内容与答案差一格"，仍错 | `L` 是通路事实，改标签只是指错格 |
| 真要让 `L=1` | 需同帧读回降采样（在游戏线程同步等 GPU）或去掉每帧 CPU 回读 | 前者把延迟换成 stall，后者会破坏残差基准（残影回归） |

**核心教训**：
```
配对错误是"几何/身份"问题，不是"时间够不够"问题。
等待均值、合成计数、超时次数都可能全绿 —— 必须看画面（错位、双轮廓），
并检查"这份答案属于第几帧"。
```

## 七、如何把这套方案搬到别的项目

### 7.1 适用条件

```
① 处理是异步的、延迟量级 ≥ 1 帧
② 输出可以缓存（不需要"本帧结果必须在同一帧内已知"）
③ 帧的所有输入可复制保存（color/MV/depth/相机参数）
④ 内存/显存允许 K 份副本（K 通常 3~6）
```

### 7.2 移植清单

```
1) 明确 L：从"输入怎么送、结果怎么读"数出真实滞后帧数（不要乐观）
2) 选 K：K ≥ L + 2（至少留一档余量）；K 越大可选余量越多，但内存线性增长
3) 画三个下标：捕获 N、喂出 N−L、呈现 N−D；检查它们 mod K 互不相同
4) 三处身份：槽位 frame / 答案 answerFrame / 每槽独立答案缓冲
5) 所有"资源下标"由 K 推导，禁止字面量
6) 等待必须有上界；失败只影响本帧合成，不得跳过喂帧
7) 验收：先看画面（错位/双轮廓），再看指标
```

### 7.3 不适合用的情况

```
· 延迟不可预测且抖动极大（此时应改为"降级直通"，而不是加槽位）
· 内存极紧（K 份颜色副本可能比收益贵）
· 结果必须同帧反馈（例如影响本帧着色的后处理）→ 属于同步依赖，不适合延迟配对
```

## 九、检查清单（改这块代码前后逐条过）

```
[ ] D ≥ L + 1 且 D ≤ K − 1，且 D % K ∉ {0, L}
[ ] 呈现前校验收到的答案帧号 == 呈现帧号
[ ] 等待超时/身份不符：只置 hasAnswer=false，绝不 return
[ ] 所有 SRV/UAV 槽位由 K 推导；堆大小 = 3K+5
[ ] 答案 buffer 段数 == K；每段 = 宽×高×4；fed 纹理每槽一份
[ ] 重建会话后：清空答案序号、重置时域状态、预热 alpha
[ ] 验收：静止看闪烁、运动看双轮廓/错位、快速切视角看拖尾
[ ] 指标只作辅助：数值全绿不等于配对正确
```

## 十、已知改进点：把"喂入通道"从 1 深扩到 K 深

### 10.1 现状（R1 的实现）

```
Worker 侧：inBuf（一份 8.3MB）+ hasIn 标志
游戏侧每帧：inBuf.swap(本帧小图) → hasIn = true → 通知
Worker 取走：local = inBuf；hasIn = false → 开始算（约 13ms）
```

等效队列深度 = **1 个待处理位**（正在算的那份不算）。所以：

```
worker 12.6ms < 帧 16.7ms  → 通常跟得上，队列几乎不会满
偶发抖动（切场景/读盘/驱动抢占）→ 新帧覆盖旧的待处理帧 ⇒ 丢一帧输入
                                  表现为：那一格没有答案 → 本帧跳过 NR（不卡、不错位）
```

也就是说，**当前实现在"喂"这一侧是靠"丢掉来不及的输入"来保持非阻塞的** —— 安全，但会损失覆盖率。

### 10.2 目标形态

```
喂入环形队列（深度 = K，或至少 max(2, D−L+1)）：
  每帧把槽位 (N−L) 的小图写进 inputRing[(N−L) % K]，并登记 frameId
  worker 按 frameId 递增顺序取；取完后该输入槽位即可被下一轮覆盖
```

收益：

| 项 | 单 inbox | 环形喂入队列 |
|---|---|---|
| worker 抖动容忍 | 丢帧即损失该格 NR | 只要总滞后不超过余量就不丢 |
| 与 D−L 的配合 | 余量再大也用不上（输入被覆盖） | 余量真正生效 |
| 内存代价 | 8.3 MB | K × 8.3 MB ≈ 50 MB（K=6） |

### 10.3 实施要点

```
· 输入槽位与"呈现槽位"用同一套下标规则（frame % K），保证一一对应
· 每个输入项必须带 frameId（对应 answerFrame 的身份链）
· worker 取作业必须严格按 frameId 递增（乱序会让答案落在已过期的格子上）
· 队列空 → worker 睡眠；队列满（实际上不会，因为每帧只写一格）→ 说明 K 选小了
· 切换模型/重建会话时：清空队列并把 frameId 基准重设，避免旧帧混入新会话
```

### 10.4 这一项与画质的关系

```
它不改善单帧画质，只改善"覆盖率"：同样的余量下，少丢帧 = 更多帧带 NR = 观感更连续
（尤其在一次性的卡顿/读盘之后，不会出现"连续好几帧没效果"的观感断层）
```

## 十一、★ 接缝清单：跨卡 / 跨厂商插入点（2026-10-29 新增）

> **来源**：TheAutomatic/dlss-5-amd-project 的 `fsr-rr` 分支 2026-10-27 ~ 10-29 的合并前修复
> （commit `3dc7e15` / `e84e0c9` / `4ff7afa` / `5355c7d` / `cb806f3` / `92d630d` / `2c6aefe`），
> 他们踩的四个坑在我们的跨卡桥上**同构存在**。原文见知识库 §14.1-A。
>
> **适用范围**：任何"我们的槽位队列 ↔ 别人的管线/别人的 GPU/别人的 API"对接处 ——
> 跨卡（D3D12↔D3D12）、跨 API（D3D12↔HIP/Vulkan）、同卡换后端（lmxxf ↔ mochizuki）、
> 以及将来若接 RR / 降噪链路（预降噪 → NR → 超分）。
>
> **用法**：动这块代码**前**逐条过一遍标 ⚠️ 的项，动完**后**逐条收证据（日志/计数/抓帧）。
> 每条都写了"怎么查"，查不出来就等于没做。

### 11.1 四条原则（先记这四句）

```
① 布局/状态只能由【录制那次转换的人】交出，任何一侧都不许猜
② 票证按槽位存，不按资源存；"最后一次录制"的单戳保护不了 K 槽在飞
③ 退休只认"队列证明完成"，不认时间；在飞的资源不许被超时强杀
④ 前提不满足就【这一帧不出 NR 并计数】，绝不拿旧答案/别的东西顶替
```

### 11.2 A 组：布局 / 状态随槽位传递（防"猜状态"）

```
[ ] A1  槽位结构体里有显式的状态字段：{layout_before, layout_after, fence_value}，
        A 侧在录制完最后一次转换后写入，B 侧只读不算
[ ] A2 ⚠️ 共享纹理的"最后一跳"必须显式落到 D3D12_RESOURCE_STATE_COMMON，
        且这一次转换必须在 fence signal【之前】录进队列 —— 顺序反了就是根治不了的花屏
[ ] A3 ⚠️ 任何"B 侧无条件按 COMMON 写 BarrierBefore"的乐观假设都要删掉：
        B 侧（尤其 HIP/Vulkan 后端）没有 D3D12 布局概念，A 侧是唯一权威
[ ] A4  同一个资源在同一帧里只允许一个"转换录制者"；出现第二个（别人的 SDK、另一个设备、
        另一个队列）→ 账本只能作废，这就是 source_layout_invalidated 的来源
[ ] A5  跨适配器共享纹理只经 keyed mutex / 显式 fence 交接，不依赖隐式同步
[ ] A6  会话重建 / 改分辨率 / 换后端后，所有槽位的状态字段必须置 UNKNOWN 并重新建立，
        不许沿用上一轮的 layout

查法（必做）：
  日志每帧打印一行  frameId, slot, layout_before → layout_after, fence_value
  判失败：出现 UNKNOWN；或 A 侧打印的 layout_after 与 B 侧读到的 layout_before 不一致；
          或 gap（同一槽位连续两次交接的 frameId 不连续却没有 skip 记录）
```

### 11.3 B 组：票证按槽位（防"拿上一轮的残留出画"）

```
[ ] B1 ⚠️ 每个槽位一份票证 {frameId, sessionGen, layout, fenceTarget}，
        不是全局一个 last_recording 戳
[ ] B2  sessionGen 在【重建会话 / 热切换模型 / 改分辨率 / 改 K】时 +1；
        票证 sessionGen ≠ 当前 → 视为无效票，丢弃，不复用
[ ] B3 ⚠️ 槽位复用前必须验证该票证已退休（见 C 组），否则就是拿残留出画
[ ] B4  身份链最终校验仍然是：收到答案的 frameId == 呈现帧号（§九第 2 条），票证只是它的前置守卫

查法：
  把 K 临时改成 3，在读盘/切场景卡顿处跑 30 秒
  期望：表现为"跳过 NR"（覆盖率下降），【不是】错位/双轮廓/区域异常
  失败形态：出现上一轮画面残留（残影 A4）、或槽位内容与帧号不匹配（错位 A1）
```

### 11.4 C 组：退休按队列证明（防"时间到了就销毁"）

```
[ ] C1 ⚠️ 退休条件 = 该批次录制所在队列的 fence 已达，或命令表被【证明】丢弃
        —— 不是"提交后 N 秒"、不是"过了 N 帧"
[ ] C2 ⚠️ 每次查询状态时，已完成条目都要视为【已退休】，
        不能只有第一次查询才翻转状态（他们的 P1 #3 就是这条）
[ ] C3 ⚠️ 超时/老化**不许**覆盖或释放仍在飞的资源：
        busy 的槽位 → 这一帧失败并跳过出画；busy 的会话 → 延迟，不 free
[ ] C4  兜底路径（discard / age）必须有界、必须记日志、必须能计数
[ ] C5  拆掉所有"固定 2 秒 / 固定 N 帧就销毁"的定时器式假设
[ ] C6  worker 真耗时改用后端自报的口径（lmxxf 的 GetTimings/网络 GPU 时间），
        而不是用 CPU 时钟推（§十一 之外，但同一类"用错证据"的错误）

查法：
  把 worker 人为拖慢到 40 ms（或把余量设 0），跑 30 秒
  期望：覆盖率下降 + 日志有 defer / skip 计数，画面正确
  失败形态：花屏、驱动重置、崩溃；或日志出现"释放了仍在飞的资源"
```

### 11.5 D 组：失败显式（防"静默降级冒充"）

```
[ ] D1 ⚠️ 任一前提不满足（票证冲突 / 布局未知 / fence 未达 / 后端初始化失败）→
        这一帧【跳过 NR，输出原始 Color】，并计入对应原因
[ ] D2 ⚠️ 禁止用任何东西顶替：不用上一帧答案、不用前 K 帧答案、不用已被否证的替代路线
        （社区反例：RR 门禁关掉时走 FSR2 回退，而 FSR2 吃到未降噪输入 = "假装降噪"）
[ ] D3  "门禁关闭"与"门禁开但能力缺失"必须区分：
        前者保持原生路由（不动别人的输出），后者显式报错 —— 不许静默换路
[ ] D4  B 端失败必须让 A 端看得见（状态位 + 计数），不能只在 B 端日志里留一行

查法：
  人为制造四种失败（布局未知 / 票证过期 / fence 超时 / 后端未创建），逐一确认：
  画面 = 原始 Color（无残影、无闪烁、无区域异常），且计数器各自 +1
```

### 11.6 E 组：日志与统计（让"为什么这帧没 NR"可回答）

```
[ ] E1  必须常驻的计数器（缺一个都等于不能定位）：
          提交帧数 / 带 NR 出画帧数 / 跳过帧数（按原因分类）/
          defer 次数 / 兜底退休次数 / 等待均值 + p99 / 布局 UNKNOWN 次数
[ ] E2 ⚠️ 拒绝原因"每次变化打一行 + 周期聚合"，不是每帧刷屏、也不是只在屏上闪一下
        （社区那条 bug：reject_causes 是空的，旁边却挂着 bridge_bypass 计数）
[ ] E3  抓帧三环节（A 喂入 / N 网络输出 / C 出画）+ 跑马灯帧号仍是错位类问题的唯一硬证据；
        本节所有条目全绿 ≠ 配对正确（承 §九最后一条）
```

### 11.7 F 组：接入"新后端 / 新 seam"时的一次性动作

```
接一个新后端（lmxxf ↔ mochizuki ↔ 将来别的）或一条新链路（预降噪 → NR → 超分）时，先回答：

[ ] F1  这个接缝在谁的内部？能不能拿到【权威布局】？
        —— 在 feature 内部（能声明布局）才能安全插；只能在外部旁观 → 只许读、不许写状态
[ ] F2  后端是 inline（录进游戏自己的 command list、同帧执行）还是 async（我们的槽位）？
        · inline → 布局权威必须在【录制前一刻】重新发布
        · async  → 布局权威必须【随槽位一起传递】（A 组）
[ ] F3  single-seam 不变式：谁跑模型，必须是全局唯一裁决点；日志里录一条 seam=<名字>
        （防止同一帧被两条接缝各跑一次 → 时间翻倍 + 效果叠加发灰）
[ ] F4  中间件是否使用 enhanced barrier（FFX SDK 就用了）？
        是 → 默认假设"账本会被作废"，提前准备 DeclareInputLayouts 的等价物：
             "声明者把已知的权威布局重新写回账本，时间点在调用下游之前"
[ ] F5  这条链路会不会跨帧持有资源（历史/常量/描述符环）？会 → 退休必须走 C 组
```

### 11.8 与六项检查（A1~A6）的经验对应

> 以下是**经验对应**，不是定理：用来决定"出现某个症状时先查哪一组"。

| 症状 | 先查 | 理由 |
|---|---|---|
| A1 错位 | **B 票证** → A 布局 | 身份链断 或 槽位内容来自错误的一轮 |
| A2 静止闪烁 | **D 失败显式** → B | 用旧答案/NR 时有时无（覆盖率抖动）都会读成"闪" |
| A3 运动中双轮廓 | **B 票证** → A 组 A6 | 两张不同帧的内容被合成到一起 |
| A4 残影 | **C 退休** → E 统计 | 复用未退休槽位 / 迟到答案被当成当前帧 |
| A5 拖尾 | **C1/C2** | 旧答案延迟交付且未被丢弃 |
| A6 区域异常 | **A 布局** → F4 | 布局猜错、tombstone、跨设备状态不一致 |

### 11.9 反例（失败形态，记下来别再犯）

```
· 让 B 侧对共享纹理无条件按 COMMON 写 BarrierBefore        → 偶发花屏，靠重跑复现不了
· 用全局 last_recording 戳保护 K 个槽位                     → K ≥ 2 后必然出残留
· "提交 2 秒后销毁"式退休                                   → 卡顿场景下释放仍在飞的资源 → 驱动重置
· 超时就把 busy 槽位强杀回收                                 → 看着"自愈"，实则用残帧出画
· 状态查询只有第一次会翻转已完成条目 → 退役不漏，池子慢性耗尽
· NR 不可用时偷偷用上一帧答案顶替                           → 拖尾/残影，且日志一片绿（最坏的一种）
· 换后端/改分辨率不清 sessionGen                           → 旧会话答案混进新会话（错位，且极难复现）
```
