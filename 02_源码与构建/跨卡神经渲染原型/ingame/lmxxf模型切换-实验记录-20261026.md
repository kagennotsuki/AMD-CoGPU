# lmxxf 模型切换实验记录（2026-10-26）

> 目的：记录"在 lmxxf 后端上尝试把模型从 Small 切回 Original"的全部尝试、原始证据与结论，
> 供另一对话做独立分析。
> 环境：RE2（DX11，REFramework 提供 XeSS 调用方）+ 我们的 libxess 代理（libxess.dll）
>       游戏渲染卡 = RX 7900 XT（DeviceId 0x744C，被改名成 "AMD Radeon RX 9070"）
>       NR 推理卡 = RX 9070 XT（DeviceId 0x7550，gfx1201）
>       跨卡方式：代理在 9070 XT 上建独立 D3D12 设备，NR 网络由 lmxxf 运行时执行

## 2. 我们做过的切换尝试（按时间顺序，全部失败）

### 尝试 1：写配置文件（照上游文档）
```
游戏目录\DLSS5-AMD\native-game-flags.txt:
  DLSS5_MULTI_PASS=1
```
结果：**无效**。运行时状态行仍是 `model=small`。
原因证据：B 这份运行时的二进制里**没有** `DLSS5-AMD`、`native-game-flags`、`default-config`、`custom-config`
这些字符串（`findstr` 逐条 miss），只有 `DLSS5_MULTI_PASS`、`DLSS5_`、`MULTI_PASS_PREDICT`。

### 尝试 2：DllMain 里设环境变量（进程最早期）
```cpp
// DllMain / DLL_PROCESS_ATTACH
SetEnvironmentVariableW(L"DLSS5_MULTI_PASS", L"1");
```
结果：**无效**。日志：
```
early: 已设 DLSS5_MULTI_PASS=1（请求 Original 71-block）
worker: #33150(槽0) 9.7 ms ok | 状态: lmxxf modules_ok=40 hip=1 net=1920x1080 color_job=1920x1080 weights=1 model=small temporal=off
```

### 尝试 3：建会话前设环境变量（WorkerInit）
```cpp
SetEnvironmentVariableW(L"DLSS5_MULTI_PASS", modelReq.c_str());
GetEnvironmentVariableW(L"DLSS5_MULTI_PASS", rb, 16);       // 回读 = 1
W.api.Create(&ci, &W.ctx);  W.api.PrepareSession(W.ctx);
```
结果：**无效**。回读确实是 `1`，但状态行仍 `model=small`、worker 仍 9.6~10.2 ms。

### 尝试 4：菜单按钮触发"重建会话"（照 AMDNR 的编排：Destroy → Create）
```cpp
// 菜单
if (ImGui::Button("切到 Original（旧模型）")) g_modelSel = 1;
// worker 线程
if (W.modelApplied != g_modelSel) {
    W.api.Destroy(W.ctx); W.ctx = nullptr;
    WorkerCreateSession();      // 内部：SetEnvironmentVariableW(新值) → Create → PrepareSession

```
结果：**重建确实发生了，模型没变**。日志（用户实测）：
```
worker: 收到换模型请求（Original 71-block），开始重建会话
worker: 建会话 → 请求 DLSS5_MULTI_PASS=1（回读 1，Original 71-block）
worker: 会话就绪 (1920x1080, 8294400 字节) 模型=Original      ← 这行是我们自己写的标签，不是运行时说的
… 状态行仍然是 model=small，worker 仍 ~9.6 ms
```
（注意坑：我们日志里的"模型=Original"来自我们自己的请求变量，**不是**运行时回报，容易误读。）

### 尝试 5：文件驱动切换（免得反复重编）
```
游戏目录\xess_proxy.model.txt 内容 "1"（或 "0.5"）
```
结果：值被正确读到并打印，**状态仍是 small**。

## 4. 目前的结论（推理，附置信度）

1. **B（1,616,896）没有模型选择通道**（置信度高）
   唯一导出是 `LmxxfNrGetApi`；`DLSS5_MULTI_PASS` 的解析代码即便存在，也**不在 runtime 路径里生效**
   （add-on 路线才有热重载与 flags 文件读取）。所以 env 无论何时设、无论重建多少次会话，都只能得到 Small。

2. **模型很可能由 pak 里的 `model-manifest.json` 决定**（中高置信度）
   运行时字符串有 `/model-manifest.json`、`"model": "small"`、`lmxxf: Small model found`、
   `missing-small-assets`。我们这份 pak（509,458,860 B，10-17）在新运行时下 `weights=1` 且跑出 Small，
   而在 A 运行时下跑的是 Original —— 说明**同一 pak 含两种权重**，选择权在运行时。

3. **C（1,530,880）才是"能切"的那一份**（高置信度）
   它有 `SetRuntimeSettings` / `SetTierPolicy` / `SupportsSmallGeometry`，且内置 `model A -> B … the network is rebuilt`
   的逻辑；AMDNR 的宿主就是靠这些接口切 A/B 的。

4. **A（1,430,640）等于"永远 Original"**（高置信度）
   它早于 Small 出现，只认 160 字节表、assets 传 pak 路径；实测 13.6~14.0 ms，正是 71-block 的量级。

3. `LmxxfNrSupportsSmallGeometry()`（无参，返回 1）是能力查询，会不会也暗示"支持 Small geometry 但需要特定 kernel 组"？
4. **Model B 只支持 1920×1152**：我们喂给运行时的是 1920×1080（`net=1920x1080`），

   这句暗示运行时**支持**在 PrepareFrame 阶段感知"模型变化"，但需要调用方以某种方式声明变化并重试。

## 7. 一句话总结

**在我们这份 lmxxf 运行时（1,616,896）上切不动模型，不是显卡/跨卡的问题，而是这份运行时没有模型选择接口**
（只有 `LmxxfNrGetApi`，只吃 136 字节 ABI）；能做到 A/B 的是 AMDNR 那份 1,530,880（10 个导出、接受 160 字节表、
内置 "model A -> B … the network is rebuilt"）。下一步要么换那份运行时 + 配套 759 MB pak 并摸清 `SetRuntimeSettings`，
要么接受"旧运行时 = 永远 Original（13.6~14 ms）"。

## 8. 独立分析结论（另一对话，2026-10-26 19:05，只读证据）

### 8.1 三份运行时的能力对照（逐条在二进制里核过）

| 能力 | **A** 1,430,640 | **B** 1,616,896 | **C** 1,530,880 |
|---|---|---|---|
| 控制导出数量 | **9 个**（GetApi/GetImportPoolStats/GetJobTimes/QueryContextCapabilities/SetDirectConsumer/**SetRuntimeSettings**/SetStreamPriority/**SetTierPolicy**/SetWarmAhead） | **1 个**（仅 GetApi） | **10 个**（A 的 9 个 + `SupportsSmallGeometry`） |
| `DLSS5_MULTI_PASS` 解析 | 0 处 | **13 处**（含 `invalid (0.5/1/2/3), using 0.5`） | 0 处 |
| `Small model found` / `missing-small-assets` | 0 | 有 | 有 |
| `model requested=%sx effective=%sx blocks=%u assets=%s reason=%s` | 0 | 有 | 有 |
| `model A -> B … the network is rebuilt` | 0 | 0 | **3 处（LMXB044）** |
| `[L44CACHE] model=%s hit=%u resources_preserved=1 slots=2` | 0 | 0 | **4 处** |
| `Model B runs only at the 1920x1152 network (this size is not ported)` | 0 | 0 | **有** |
| `Model B needs the wave-owned, C512 M32 and ViT N64 kernel groups and the graph off` | 0 | 0 | **有** |
| `small/model-manifest.json` | 0 | 0 | **2 处** |
| 实测跑什么 | 永远 Original（无 Small 代码） | Small 9.6~10.2ms | 需配套资产，未验 |

**修正原表两处**：① A **不是**"没有控制接口"，它有 9 个导出；它只是**完全没有 Small 相关代码**（0 处字符串），所以"永远 Original"是编译期决定的，不需要切。② C 的 `SupportsSmallGeometry()` 反汇编是 `mov eax,1; ret`（恒 1）。

### 8.2 C 的接口签名（反汇编实测）

```
LmxxfNrSetTierPolicy(ctx, uint32 tier)                  ← 两参数（rcx=ctx, edx=tier）
LmxxfNrSetRuntimeSettings(ctx, const void* p, uint32 size)   ← 三参数（与 A 同形）
LmxxfNrSupportsSmallGeometry()                          ← 恒返回 1
```

`SetRuntimeSettings` 的结构体校验（早期对 A 的反汇编，C 同形）：
`+0 u32 struct_size ∈ {16,20}`、`+4 f32`（有限且 ≥0，被上限钳制）、`+8 bool`、`+0xC u32 ≤2`、`+0x10 bool(仅 size=20)`。
**`+0xC` 那个 ≤2 的整数最可疑**（0/1/2 像枚举），但尚未证明是模型选择。

### 8.3 为什么 B 切不动（结论）

```
B 只有 LmxxfNrGetApi 一个导出 ⇒ 会话内【没有任何命令通道】可以要求换模型。
它的 DLSS5_MULTI_PASS 解析即便存在，也只能在初始化阶段生效（或属于 add-on/RE9 宿主路径），
所以"设环境变量 / 重建会话 / 文件驱动"全都无效 —— 与实验记录一致。
另：排除了 "缺 hipMemcpy2DAsync 导致退化" 这个假设（System32\amdhip64_7.dll 里有该导出）。
```

### 8.4 真正能切的是 C，但它有三个硬前提（来自 C 自己的字符串）

```
① 几何：Model B 只跑 1920×1152 网络（"this size is not ported"），我们喂 1920×1080 ⇒ 会被拒
② kernel 组：需要 wave-owned + C512 M32 + ViT N64 三组，且 graph 关掉
      （对应环境变量：DLSS5_HIP_WAVE_OWNED / DLSS5_HIP_C512_M32 / DLSS5_HIP_VIT_PROJ_N64 …）
③ 权重：需要 small/model-manifest.json 那一套（对应 759 MB 的 pak）
另外它有 [L44CACHE] resources_preserved=1 slots=2 —— 切换时保留旧模型资源，说明切换是"重建网络但缓存资源"
```

### 8.5 已做的探针实验（未改动任何游戏文件）

## 9. 决定性实验（另一对话，2026-10-26 19:30）：B 忽略 DLSS5_MULTI_PASS

### 9.1 新工具

```
src/lmxxf_frame_probe.cpp  →  build\Release\lmxxf_frame_probe.exe
· 通用 ABI 探针（依次试 160 / 144 / 136，FrameInfo 随之 160 / 104 / 80）
· 自己建 D3D12 设备（优先 DeviceId 0x7550）+ 计算队列 + 1920x1080 彩色纹理（UPLOAD 填充）
· 真实跑帧：PrepareFrame → RecordInputs → Execute → ExecuteAfterProducer → RecordOutputs → GetStatus
· 资源目录由 LMXXF_ASSETS 指定；模型请求由环境变量 DLSS5_MULTI_PASS 指定
```

**资源目录的正确构造（踩坑记录）**：
```
· Create 要求目录里有 SHA256SUMS + hsaco  ⇒ 必须是 lmxxf-modules（或其复制）
· PrepareFrame 又要 native_codec_encode.hlsl ⇒ 该 hlsl 必须在【DLL 所在目录】（放 assets 里无效）
  实测：把 shaders\*.hlsl 复制到 exe/DLL 同目录后，PrepareFrame 才通过
· 权重在 native-game-tiled-assets\（460 个文件，含 noise.f32）；可用 junction 挂进来
```

### 9.2 三组对照（同一份 B：1,616,896 / FA18D719，assets 已备齐）

```
DLSS5_MULTI_PASS=(unset) → model requested=1x effective=1x blocks=71 assets= reason=original
DLSS5_MULTI_PASS=1       → model requested=1x effective=1x blocks=71 assets= reason=original
DLSS5_MULTI_PASS=0.5     → model requested=1x effective=1x blocks=71 assets= reason=original
（每次都在随后崩溃 0xC0000005，怀疑权重路径/后续阶段，待查）
```

**结论：B 这份运行时对 DLSS5_MULTI_PASS 完全不敏感，恒为 Original（71 块）。**

### 9.3 由此推翻/修正的旧结论

```
❌ 旧："B = Small 运行时，跑到 9.6~10.2ms，切不回 Original"
✅ 新：B 恒为 Original；"model=small + 9.6~10.2ms" 那组数据很可能来自
      【mochizuki 改名冒充的那份 DLL】（同为 06:15 写入，SHA 9E7C9BAF，状态行会打印 model=small，
        且其 2-pass 实测正好 9.6ms）—— 与 B 的 71 块输出不是一回事
待验：用同一个探针指向 mochizuki 那份，确认它的状态行确实是 model=small
```

## 10. 再下一层：B 的"模型"由【权重集是否存在】决定，不是环境变量（2026-10-26 19:50）

### 10.1 游戏目录里其实有【两套】权重

```
native-game-tiled-assets\            ← Original（71 块）资产
    block*.f32/.f16           178 个
    noise.f32                 192 MB
    normalized-output.f32      32 MB
    hwc-to-vit.i32 / vit-to-hwc.i32  各 2.5 MB
    head-matrix.f16、post70-*、decoder39-weights.f16
    以及全部 native_*.hlsl / *.cso（着色器就在这儿）
native-game-tiled-assets\small\      ← Small（31 块）资产
    block*.f32/.f16            86 个
    model-manifest.json       25 KB
    post70-history-head.f16    ← Small 专用历史头（与 C 里 0x3A23 混合尺度对应）
```

### 10.2 B 的模型选择规则（实测）

| 条件 | 运行时自报 |
|---|---|
| DLL 同目录**没有** `native-game-tiled-assets` | `model requested=1x effective=1x blocks=71 reason=original` |
| DLL 同目录**有** `native-game-tiled-assets`（含 `small\`） | `model requested=0.5x effective=0.5x blocks=31 reason=small-ready` |

并且：`DLSS5_MULTI_PASS` 取 `(unset)/0.5/1/2/3/7` **六种值输出完全相同**
（`requested=0.5x … reason=small-ready`，且 `multi_pass=1` 恒定）
⇒ **B 完全不读这个环境变量；它的模型由权重集是否存在决定。**

### 10.3 于是"切模型"在 B 上是【换资产】而不是【热切换】

```
想要 Original：让运行时看不到 small\（改名为 small.off，或只提供根目录权重）
想要 Small   ：保留 small\
两者都必须【重建会话】（权重在 PrepareSession/首帧装载，不是运行中可换）
⇒ B 没有热切换能力，这点与之前结论一致，但机制完全不同（不是"锁死 small"，而是"看资产"）
```

### 10.4 仍未解决：探针在 model 行之后崩溃

```
现象：打印 model requested/effective 与 multi_pass 后，0xC0000005（GetStatus 的 hip=0 说明 HIP 尚未就绪）
可能原因（未验证）：
  ① HIP 模块加载阶段需要别的路径（lmxxf-modules 与权重目录的分工尚未完全摸清）
  ② 我们的 FrameInfo80 / Job 与 B 的 136 ABI 仍有一处不匹配（代理里是 160+104 的那套）
  ③ 缺少 native-game-flags/native 配置层或 amd_comgr 依赖解析
下一步：把探针的崩溃点用 SEH 包住打印阶段名；或对照代理的 136 路径逐字段比对
```

## 11. 探针工程化过程与最终结论（2026-10-26 20:20）

### 11.1 探针演进（lmxxf_frame_probe）

```
v1 通用 ABI（160/144/136）+ 真跑帧 + GetStatus  → 能打印 model requested/effective
v2 加 SEH 分阶段（PrepareFrame/RecordInputs/ExecuteAfterProducer/RecordOutputs/GetStatus）
v3 FrameInfo 尺寸可覆盖（argv[2]）→ 证明 B 只接受 80（104/160 均报 struct_size mismatch）
v4 加 CoInitializeEx(MTA) → 崩溃点不变（排除 COM 未初始化）
```

### 11.2 资源目录的准确规则（实测，踩了三次）

```
① Create 需要目录含 SHA256SUMS + hsaco            → assets 必须是 lmxxf-modules（复制或原件）
   （错误串："Create: modules directory needs SHA256SUMS + hsaco (or HIP/ under assets)"）
② native_codec_encode.hlsl 必须在【DLL 所在目录】    → 放 assets 里无效
   （错误串："PrepareFrame: native_codec_encode.hlsl not found"）
   这也是游戏里为什么正常：游戏根目录 = exe 目录 = DLL 目录，shaders 就在那儿
③ 权重（native-game-tiled-assets，含 small\）也必须在【DLL 所在目录】
   → 决定 B 选 Small 还是 Original（见 §10）
④ 全部放同一个目录（modules + hlsl + tiled junction）也能通过 Create/PrepareFrame 前置检查
```

### 11.3 未解决的崩溃（诚实记录）

```
现象：PrepareFrame 内部、打印 "model requested=..." 之后，进程 0xC0000005 直接终止；
      我们的 SEH 抓不到（说明发生在运行时内部线程），GetStatus 的 hip=0 表示 HIP 尚未就绪。
已排除：ABI 尺寸错（80 是对的）、FrameInfo 104/160（直接 mismatch）、COM 未初始化、shaders/权重缺失。
未试：queue 类型（DIRECT vs COMPUTE）、color 纹理状态/绑定、命令行/配置层、
      运行时要求的其它环境变量（如需 graph off / wave-owned 等）。
影响：暂时无法在离线探针里量出 B/C 网络时间，也无法观察 C 的 "model A -> B" 切换日志。
拐点建议：直接用【游戏里的代理】验证 —— 代理本来就能跑通（在线程内、设备/队列/命令列表都符合），
        只要把"模型"当作【资产 + 重建会话】来切换即可。
```

### 11.4 对项目的最终结论与建议方案

```
事实：
  A（1,430,640） 没有 Small 代码 → 永远 Original，无法切
  B（1,616,896） 不读 DLSS5_MULTI_PASS；模型 = small\ 是否存在 → 只能靠换资产切（且需重建会话）
  C（1,530,880） 有 A/B 切换机制（model A->B rebuilt / L44CACHE / SupportsSmallGeometry），
                 但要求：1920×1152 网络几何 + wave-owned/C512 M32/ViT N64 三组 kernel + graph off
                 + small/model-manifest 权重；换模型是"重建网络但保留资源"

建议（按成本从低到高）：
  ① 冷切换（最简单，今天就能做）
     我们的代理已有"Destroy → Create → PrepareSession"的会话重建能力；
     把模型切换实现为：改 small\ 的有无（或切 DLL）→ 重建会话 → 画面在 1~2 帧内恢复
  ② 双实例交替（真正的"无缝切换"，也是 3zwr1 Model interleave 的思路）
     同时持有两个运行时实例（旧模型 / 新模型），按帧或按秒交替取结果；
     切换时无需重建、无黑帧，代价是显存翻倍
  ③ 追 C 的 API（成本最高）
     需要先解决 §11.3 的崩溃，再摸 SetRuntimeSettings(+0xC 那个 ≤2 的整数) / SetTierPolicy，
     即使成功也要满足 1152 几何与三组 kernel 的硬条件
```
