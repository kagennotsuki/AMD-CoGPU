# 离线对比图：可复现流程（已验证通过）

> 2026-10-24。**这条流程已经跑通并验收**：从游戏里抓一帧真实数据 → 游戏外喂 lmxxf → 出「NR 前 / NR 后 / 差分」对比图。
> 两条路径都可用：**A 独立离线工具**（最简单，用来验证网络效果）和 **B 消费端适配层**（将来接 MGPU）。
> 复现时对着本文的「验收数值」比对，数字对得上就说明链路没坏。

---

## 一、五步复现（路径 A：独立离线工具）

### 第 1 步：把抓帧版代理装进游戏

```
ingame\capture_install.bat
```

它做三件事：真身改名 `libxess_orig.dll`、代理放成 `libxess.dll`、写 `xess_proxy_capture.txt`
（抓帧模式；**这条路径完全不碰 NR 链路，所以不会触发我们 v7 那个崩溃**）。

### 第 2 步：进游戏，抓一帧

两种触发方式，任选：

- 游戏内按 **F2**；
- 游戏运行时双击 `ingame\capture_trigger.bat`（往游戏目录丢 `xess_proxy_capnow.txt`，代理几帧内自动抓）。
  —— 远程/脚本自动化就用这个，**已实测有效**。

抓帧是异步的：触发后 **90 帧**（约 0.5 秒）才回读，**不卡帧**。产物落在游戏目录：

| 文件 | 内容 | 大小（4K 实测） |
|---|---|---|
| `nr_cap_out.bin` | pOutput 3840×2160 fmt=24 —— **这一帧不经 NR 的最终画面** | 33,177,600 |
| `nr_cap_color.bin` | pColor 2227×1253 fmt=87（上采样前） | 11,161,724 |
| `nr_cap_depth.bin` | 深度 2227×1253 fmt=19（D32S8） | 11,161,724 |
| `nr_cap_mv.bin` | 运动矢量 2227×1253 fmt=13（RGBA16 SNORM） | 22,323,448 |
| `nr_cap_color.bmp` / `nr_cap_out.bmp` | 两张可视化（可直接看） | — |
| `nr_cap_params.txt` | 几何/格式/40 个 qword 参数/jitter/exposure | ~900 B |

> 每次抓帧**覆盖**同名文件；要留多帧就先改名。

### 第 3 步：游戏外跑 NR

```
build\probe_run\nr_from_capture.exe
```

（**必须在 `build\probe_run\` 这类干净目录里跑**，见第六节坑 2。）
输出到 `E:\AI\_归档\tmp\nr_capture\`：`nr_before.bmp` / `nr_after_x1.bmp` / `nr_after_x4.bmp` /
`nr_diff_x8.bmp` / `nr_fed1080.bmp` / `nr_fed1080_norm.bmp`。

它会跑三种喂法并打印 edit 幅度（**这就是网络的真实改动量**）：

```
[只有颜色]            edit 平均 0.0360 最大 0.4039 | 变化(>=2/255) 88.47%
[颜色 + 运动矢量]      edit 平均 0.0503 最大 0.8471 | 变化(>=2/255) 92.42%   ← 调 passes=3
[颜色 + 运动矢量 + 深度] edit 平均 0.0503 最大 0.8471 | 变化(>=2/255) 92.42%   ← 深度当前惰性
[颜色(曝光归一) + MV + 深度] edit 平均 0.0378                                  ← 最终采用
```

### 第 4 步：生成对比图

```
python tools\make_compare.py
```

产出（`E:\AI\_归档\tmp\nr_capture\`）：`cmp_crops.png`（2×2 拼图：NR 前 / ×1 / ×4 / 差分×8）、
`nr_before_1600.png`、`nr_after_x1_1600.png`、`nr_after_x4_1600.png`、`nr_diff_x8_1600.png`。

### 第 5 步：验收（数值对得上才算对）

```
python tools\check_frame.py      # 比较 nr_before.bmp 与 nr_after_x1.bmp
```

**通过标准**（4K、曝光归一后的正常结果）：

| 指标 | 期望值 |
|---|---|
| 有符号平均偏移 (R,G,B) | 接近 0（实测 **(+0.12, +1.05, +2.39)**；若出现 ±5 以上 → 曝光归一没生效） |
| 绝对平均改动 | **9~13 / 255** |
| 亮度漂移 | **< 1.5 / 255**（> 4 说明在整体提亮，不是细节） |
| **梯度能量（锐度）** | **+20% 左右**（实测 5.181 → 6.385 = **+23%**）← 这是「NR 真的起作用」最硬的指标 |
| 亮度相关性 | 0.85~0.93（≈1 说明没错位；明显偏低要查时间对齐） |

## 二、路径 B：消费端适配层（接 MGPU 用）

```
build\probe_run\mgpu_consumer_test.exe [strength] [frames]
```

模拟「已经跨卡拷到 GPU1 的纹理」→ 适配层自动缩到 1080p、跑 lmxxf、把答案叠回 4K。
输出 `E:\AI\_归档\tmp\mgpu\mgpu_out_s<strength>.bmp` 与 `mgpu_in.bmp`，然后：

```
python tools\make_adapter_cmp.py     # 三联 1:1 对比 + 全画面 + 差分
```

**已验收数值**（strength=1.0，5 帧）：帧耗时 **约 36 ms**、`passes=3`、
输出与输入平均差 **12.9/255**。注意这一次**含 +13/255 的整体提亮**（见第六节坑 6）。

### 适配层的调试模式（排同类问题非常快，建议保留）

`strength` 传特殊值即可切换输出内容：

| strength | 输出 | 用途 |
|---|---|---|
| `-2` | 喂进网络的那张图（1080p） | 验证降采样/增益，**应≈输入** |
| `-3` | 直接采样输入纹理 | 验证输入纹理与 SRV（**应逐像素等于输入，实测差 0.0**） |
| `-4` | 增益值（整屏灰=增益×255） | 增益链路是否生效 |
| `-5` | 累加器整数（R/G/B 拼成 24 位） | 曝光归约是否工作 |
| `0` | 网络答案（private_output/gain） | 答案是否非空 |
| `< 0` 其它 | \|答案 − 输入\| × 8 | 看 edit 是否真非 0 |
| `1.0` | 正常输出（base + edit） | 正常观感 |

## 四、关键事实清单（写代码时别忘）

1. **网络结果只在 `job.private_output`**；`fi.color` 逐字节不变。取结果要在 `Retire` **之前**，
   用 `COMMON→COPY_SOURCE→COMMON` 拷贝，**不要**直接建 SRV 采样（实测采出来是 0）。
2. **颜色预算 ≤1920×1080**（2.07M 像素）——**这是 lmxxf 这个运行时（这份 pak）特有的准入策略，
   不是我们的设计约束，也不是显卡限制。后续换别的运行时，这条限制可以去掉。**
   证据：`QueryCapabilities` 自报 `max_input_width/height = 1920/1080`；其头文件写明「admission is by pixel budget」
   （所以 ≤2560 宽、总像素不超预算的超宽也能过）；拒绝由它内部 codec 抛出 `codec unverified input format/geometry`。
   4K 或 2227×1253 会被拒，而且**会把会话打成 `session is poisoned`**，之后全部 UNAVAILABLE → 必须销毁重建。
   **代码上的准备**：现在 `mgpu_nr_consumer.cpp` 里硬编码了 `budget = 1920*1080`；换运行时时应改成
   「先用 `QueryCapabilities` 问这个运行时能接多大，拿不到再退回 1080p」，也就是把**网络输入尺寸当能力/参数，而不是常量**。
   即便如此，成本仍要算：1440p 网络 ≈ 2 倍像素（25~30 ms），原生 4K 不现实 —— 所以「抬 edit 质量」比「抬输入分辨率」更划算。
   （另：运行时确实还有 1728×972 / 2560×1440 / 原生 up to 3840×2160 的**网络尺寸**档位，但需要
   ① 能查到显存余量（我们这里它报 "this GPU did not say how much is left" → 一直留在 1080 档）、
   ② tier policy / `AMDNR_DEV_NETWORK_HEIGHT`、`AMDNR_NATIVE_PW/PH` 等开关、③ 原生路径还需另一套资产 native-pak。）

3. `struct_size` 只有 **120 / 144 / 160** 合法（160 = 带历史掩码）。
4. **必须做曝光归一**：运行时把输入均值拉向 0.5 中灰，不归一会整体提亮（实测 +5/255 且偏暖）。
   做法：`增益 = 0.5/均值` 先乘进去、答案再除回来。
5. **motion 有用**（passes 1→3、edit 幅度上升），**depth 当前惰性**（有无输出逐字节同级）。
6. 控制量用 `ctl = tone 1 / structure 1 / skin 3 / other 2 / style 0`（与 AMDNR 实测一致）。
7. 叠加（`base + edit`）而不是整幅替换，才能保住帧尺寸的原生细节。

## 六、踩过的坑（按踩到的次数排序）

1. **游戏目录里的中文路径会给 `fopen` 找麻烦**：所有 C 工具的**输出目录必须纯 ASCII**
   （用 `E:\AI\_归档\tmp\...`）。`CreateDirectoryA` 带中文会建出一个乱码目录，而且 `fopen` 也写不进去。
2. **`build\Release\` 里放着 dxgi/d3d12 代理 DLL**：在那里跑任何 exe 都会被劫持，
   `CreateDXGIFactory2` 直接 `E_FAIL`（旧工具 `nr_*` 报错就是这个原因）。**离线工具一律放 `build\probe_run\`**。
3. **`.ps1` 必须 UTF-8 BOM，`.bat` 内容必须纯 ASCII**：否则 PowerShell/cmd 按 ANSI 读，
   中文路径和字符串会把脚本解析坏。批量脚本宁可用「内联 pwsh 命令」或 Python 脚本。
4. **`far` 是 windef.h 的宏**，不能当变量名（编译报「语法错误: =」）。
5. **通道顺序**：`R10G10B10A2` 解包出的 CPU 数组是 RGBA，但上传进 `B8G8R8A8` 纹理要按
   **BGRA 摆字节**；BMP 存盘时也要分清源是 RGBA 还是 BGRA（坑过我两次，表现为「整幅 R/B 互换」）。
6. **曝光增益恒等（1.0，已知未修）**：GPU 侧均值归约读不出正确值（累加器读到 ≈0.5），
   表现为画面整体亮 **+13/255**。修法已备：把 P1/P2 拆成两次提交（`build/fix_split.py`），
   或用「上一帧的 CPU 均值」。**幅度不大，先记着。**
7. **UAV 槽位绝不能共用**：适配层里 `S_DST` 曾被「写颜色」和「写输出」共用 → `colourSmall` 永远 0；
   depth/mvec 的降采样又共用同一个槽位 → **把颜色覆盖成运动矢量**。两个 bug 表现完全一样（输出≈输入）。
8. `private_output` 全 0 不一定是 bug：运行时头文件写明 `EnqueueHip` 在 recovery 后会把私有输出
   **整体清零再返回 OK**，即「报成功但答案全 0」是它表达「这张输入我不用」的方式。
