## 0. ⚠ 首要：命名冲突，先统一口径

安装器现有文档 [README-安装程序.md](../../08_工具与脚本/安装程序/README-安装程序.md) 第 6 行写的是：

```

```

**它里面的「方案 B」= 自托管**（自己托管一份 runtime.zip，安装器优先下载它）。

而本文要推动的策略与它**正好相反**。为避免两个对话互相误解，本文统一使用新名字：

| 本文用名 | 含义 | 与旧文档的对应 |
|---|---|---|
| **自托管模式** | 作者托管 `runtime.zip`，填 `selfHosted.url`，安装器优先下载 | 即旧文档的「方案 B」 |
| **零分发模式** | 发布包**不含**运行时，安装器只从上游下载；作者不托管任何第三方内容 | 本文新增建议 |

> 建议顺手把旧文档里的「方案 B」改名为「自托管模式」，避免后来人继续混。

## 1. 为什么要求改（背景，不需要你重新论证）

运行时**不是本项目的东西**，自托管它等于作者成为分发者，会同时继承两条风险：

1. **`LmxxfNrRuntime.pak`（509,458,860 B）是 AMDNR 的构建物**
   证据：pak 头部声明 `RDNA 3 (gfx11) backend: AMDNR - lmxxf RDNA 3 backend by 3zwr1`；
   本机文件与 AMDNR 包内同名文件 SHA256 一致（`270991761A5FC615…`）。
   AMDNR 是 **GPL-3.0**，而其**源码要到 0.5.0 才公开**（见其 `AMDNR_NOTICE.txt` §6）
   ⇒ 分发这个二进制却无法提供对应源码，是 GPL-3.0 §6 的问题。
2. **模型源自 NVIDIA 的 DLSS 5 网络**（社区统一口径：任何包都不含，用户自备）。

只分发自己的代码，这两条都不触发。**目标：发布包只含 `libxess.dll` + 脚本 + 许可文件。**

已实测：排除 `payload\runtime` 后，发布包 **915 MB → 0.4 MB**。

## 3. 已知问题（共 4 个，按严重度）

### P1【阻断】零分发模式下，拿不到代理需要的文件

**位置**：`runtime-manifest.json:22-23`

```json
"proxyRequires": ["LmxxfNrRuntime.dll", "LmxxfNrRuntime.pak"],
"_兼容性说明": "…上游 DLSSNR-AMD 的 Windows 包提供 dlssnr-amd.asi 与 CC_* 模型，
                不含这两个文件名。安装器会在解压后检查 proxyRequires：不齐备就明确报
                『与代理不兼容』…"
```

**事实**：

- 上游 `DLSSNR-AMD-Vulkan-Windows-0.0.7-preview-x86_64.zip` 只有 **197,734,206 B（188 MB）**
- 而代理需要的 `.pak` 单个就 **509,458,860 B（486 MB）** ⇒ **上游包里根本没有这个文件**
- 且上游不含 `LmxxfNrRuntime.*` 这两个文件名

**现状是"必然失败"，不是"可能失败"**：`README-安装程序.md` 第 109 行写的是"可能触发兼容性检查失败"，
按上面两条，是**一定**触发 —— `Install-Component` 第 214-219 行会抛"与代理不兼容"。

**这决定了零分发模式能不能成立，需要决策：见 §4。**

### P2【体验 bug】第 6 步「下一步」不会随单选项更新，用户会以为卡死

**位置**：`AMD-CoGPU-Setup.ps1:915` 与 `:901-903`

```powershell
# 915（页面渲染时求值一次）
$btnNext.Enabled = ($rSkip.Checked -or ($comps.Count -gt 0 -and
                    $comps[0].selfHosted -and $comps[0].selfHosted.url -and
                    $comps[0].selfHosted.url -notlike '*<*'))

# 901-903（三个单选的 CheckedChanged）
$rSkip.Add_CheckedChanged(({ if ($rSkip.Checked) { $S.RuntimeMode = 'skip' } }).GetNewClosure())
```

**问题**：三个 `CheckedChanged` 只改 `$S.RuntimeMode`，**没有重算 `$btnNext.Enabled`**。
而 `Show-Page`（第 665 行）只在**整页重渲染时**才重设按钮状态。

**现象（零分发模式下，即 `selfHosted.url` 为空、`payload\runtime` 不存在）**：

1. 进入第 6 步，默认选中「自动」→ 915 行求值为 `$false` → **「下一步」是灰的**
2. 用户改选「跳过」→ 事件只改 `$S.RuntimeMode`，**按钮仍是灰的**
3. 用户此时没有任何提示，只能认为安装器坏了

**现有绕过**（说明不是死锁，但用户不会想到）：
选「跳过」→ 点「上一步」→ 再点「下一步」重新进第 6 步。
重进时 896-900 行会按 `$S.RuntimeMode` 把「跳过」勾上，915 行这才求值为 `$true`。

**建议修法**（二选一，不要两个都改）：
- ① 在三个 `CheckedChanged` 里补一次重算 `$btnNext.Enabled`（抽成一个局部函数，避免复制三份）
- ② 把 915 行改成不依赖 `selfHosted.url`：例如「`comps.Count -gt 0` 就放行」，
  把"下不到"的判断留给运行时阶段报错（安装器本来就在 214-219 行有明确报错）

> 按工作区纪律：**改前备份 `AMD-CoGPU-Setup.ps1` 为 `.bak-<目的>`，一次只改一处，改完重建并校验。**

### P3【一致性】`发布运行时.ps1` 与零分发模式冲突，容易被误用

`发布运行时.ps1` 的作用就是"打包整个 `payload\runtime` + 改写 `selfHosted`"，也就是**把人拉回自托管模式**。

**风险**：将来任何一次跑它（或照 `README-安装程序.md` 第 28-41 行的"给作者"步骤操作），
就会重新变成分发第三方内容，而作者可能已经忘了这件事。

**建议**：
- 在 `README-安装程序.md` 顶部标注「零分发模式下**不要**运行本脚本」
- 或给 `发布运行时.ps1` 加 `-Disabled` 开关 / 开头打印一行警告

## 4. 需要决策的三条路（**请不要自行选择，等用户拍板**）

| 选项 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **B1 用户自备运行时** | 第 6 步改为「检测到 / 请自行放入 / 跳过」，不做下载 | 作者零分发，最干净 | 用户体验最差（要自己弄 915 MB）；改动中等 |
| **B2 指向上游 lmxxf** | 清单 `url` 改指 `lmxxf/dlss5-on-amd-9070xt-porting` 的 release（MIT，221★，提供 `LmxxfNrRuntime.dll` + `.pak`） | 改动最小（只改清单） | 拿到的是 lmxxf 71-block 网络 = 13.6~14 ms，B 形态从 60fps 退回 **55~60fps**；还需核其 ABI 版本是否匹配代理的 160 字节 FrameInfo 表 |
| **B3 混合** | `dlssnr-amd\` 从 mochizuki 下载（188 MB，MIT ✓），`.dll/.pak` 由用户自备 | 折中 | 改动中等；仍要求用户找那个 pak |

> 对外发布方向**倾向 B1**：运行时恰恰是最不该由作者分发的部分。
> 但 B1/B2 都会**改变运行时的网络与性能**，属于功能决策，必须由用户定，并且改完要重跑六项检查。

## 9. 接手方回复（安装器这边，2026-10-29 23:05）

### 9.1 ⚠ §1 的结论需要更正（有二进制原文证据）

§1 写的是「`LmxxfNrRuntime.pak` 是 AMDNR 的构建物，AMDNR 是 GPL-3.0，分发它是 §6 问题」。

**实测该 pak 自带声明的原文**（直接读 pak 二进制头部明文区，未做任何修改）：

```
LmxxfNrRuntime.pak - AMDNR, DLSS 5 neural rendering on AMD GPUs
lmxxf's network, weights and kernels: Copyright (c) 2026 Kien (lmxxf), MIT licence
  https://github.com/lmxxf/dlss5-on-amd-9070xt-porting
RDNA 3 (gfx11) backend: AMDNR - lmxxf RDNA 3 backend by 3zwr1
  Copyright (c) 2026 3zwr1 (AMDNR), MIT licence (Licenses\AMDNR_RDNA3_BACKEND.txt)
If you redistribute this file or anything taken from it, keep this notice and both credits.
This notice is authenticated: a pack whose notice was edited or removed is refused by the runtime.
```

要点：

1. **两半都是 MIT**：网络/权重/内核 = Kien(lmxxf)，RDNA3 后端 = 3zwr1(AMDNR)。
   `AMDNR_NOTICE.txt` 也把"lmxxf 的 fused C32 kernels（Kien, MIT）"等列为非 GPL 部分；
   GPL-3.0 覆盖的是 AMDNR **主项目源码**，不是这份 pak 的内容。
2. **再分发是被明确允许的**，唯一条件是：**保留包内声明 + 两条署名（Kien / 3zwr1）**。
3. **声明是运行时认证的**：任何编辑/删除都会让运行时拒绝加载该 pak。
   ⇒ 我们分发时**必须原样分发**（也正好意味着"不许为了省事改包"）。
4. 本机证据：pak `509,458,860 B`，SHA256 前16 = `270991761A5FC615`
   （payload 副本 / 游戏目录 / 基准三处一致，未被任何工具改动）。

**因此**：B1/B2/B3 里"分发 pak 有硬性许可障碍"这一前提**不成立**；真正的约束只是"保留声明与署名"。

## 12. 安装器文案修订 + 一个必须记住的编码坑（2026-10-30 00:10）

### 12.1 改了什么（纯文案，不动逻辑）

用户要求：第 1 页「小键盘 1（NumLock 关）」这一条要**附上它对应的实际功能键**——有些键盘没有小键盘，但有那个键。
代码里热切换读的是 `GetAsyncKeyState(VK_END)` + `NumLock 关闭`，所以那个"实际功能键"就是 **End**（NumLock 关时小键盘 1 本身就发 VK_END，两者同键）。

### 12.2 ★ 坑：改 .ps1 必须保住 UTF-8 BOM

用外部编辑器/工具（包括 AI 的文件编辑）改写这个脚本时，**BOM 会被吃掉**。PowerShell 5.1 对"无 BOM 的 .ps1"按 ANSI(936) 解码 →

```
现象：整个脚本报 "The hash literal was incomplete." / "Missing closing ')'" 一堆解析错误，
      中文全变乱码（组件 {0}，从上游下载… → 缁勪欢 {0}…），脚本根本跑不起来
证据：修复前文件头 = 23 72 65（#re）；正常文件头 = EF BB BF 23 72 65
```

**纪律**：每次改完 `.ps1`，先查文件头三个字节是否 `EF BB BF`，再做语法检查：

```powershell
$f = 'AMD-CoGPU-Setup.ps1'
$b = [System.IO.File]::ReadAllBytes($f); (($b[0..2] | % { $_.ToString('X2') }) -join ' ')   # 必须 EF BB BF
$err = $null; [void][System.Management.Automation.Language.Parser]::ParseFile($f,[ref]$null,[ref]$err)
if ($err.Count) { $err[0].Message } else { '语法 OK' }
```

丢掉 BOM 的修法（不丢内容，只补 BOM）：

```powershell
$t = [System.IO.File]::ReadAllText($f, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($f, $t, (New-Object System.Text.UTF8Encoding($true)))
```
